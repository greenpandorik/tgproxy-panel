# Установка и запуск панели

English version: [setup.en.md](setup.en.md)

TGProxy Panel — панель управления Telegram-прокси (MTProto, WEB и Fake-TLS): один Go-бинарь со встроенным веб-интерфейсом, PostgreSQL и Caddy для TLS. Панель ставится на отдельный сервер и управляет серверами, на которых работает telemt (по умолчанию) или официальный `tproxy-server` + MTProxy. Все скриншоты ниже сняты на демо-данных.

![Дашборд](screenshots/ru/dashboard.png)

## 1. Что понадобится

| Компонент | Требование |
|---|---|
| Сервер панели | Linux с Docker и Docker Compose v2, 1 CPU / 1 GB достаточно; домен с A-записью на этот сервер; открытые порты 80 и 443 |
| Для установщика `install.sh` | Чистый сервер Ubuntu 22.04+ или Debian 12+, root, порты 80 и 443 свободны. Docker скрипт ставит сам |
| Каждый сервер | Отдельный VPS: Ubuntu 22.04+ или Debian 12+, x86_64, публичный IPv4, свой домен (A-запись), root или sudo, открытые 80 и 443 |
| Для разработки без Docker | Go 1.26+, Node 22+, PostgreSQL 16 |

Серверы и панель должны стоять на разных хостах, потому что сервер занимает порты 80 и 443 под себя.

## 2. Вариант A: сервер с доменом (рекомендуется)

Панель работает за Caddy, который сам получает сертификат Let's Encrypt.

### Одной командой

Нужен чистый сервер Ubuntu 22.04+ или Debian 12+ с root. A-запись домена уже должна указывать на него, порты 80 и 443 должны быть свободны. Скрипт ставит Docker, если его нет, скачивает compose-файлы последнего релиза в `/opt/tgproxy-panel`, генерирует `.env` с секретами, запускает стек, ждёт готовности и создаёт первого администратора (роль `owner`).

```bash
curl -fsSL https://raw.githubusercontent.com/greenpandorik/tgproxy-panel/main/install.sh | sudo bash
```

Скрипт спросит домен, e-mail для Let's Encrypt, логин и пароль администратора (если оставить пароль пустым, скрипт его сгенерирует). Без вопросов:

```bash
curl -fsSL https://raw.githubusercontent.com/greenpandorik/tgproxy-panel/main/install.sh | sudo bash -s -- \
  --domain panel.example.com --email admin@example.com --admin-user root --admin-password 'надёжный-пароль' --yes
```

В конце скрипт печатает адрес панели и, если пароль не задан, сгенерированный пароль. Он показывается один раз. В `/opt/tgproxy-panel` лежат `docker-compose.yml`, `Caddyfile`, `.env` (права 0600) и копия скрипта. Сохраните копию `.env` вне сервера: `MASTER_KEY` шифрует все секреты в базе.

```bash
sudo /opt/tgproxy-panel/install.sh --update              # обновить до последнего релиза (или --version 1.2.0)
sudo /opt/tgproxy-panel/install.sh --uninstall           # остановить; спросит, удалять ли тома с данными
sudo /opt/tgproxy-panel/install.sh --uninstall --purge   # удалить контейнеры, тома и каталог
cd /opt/tgproxy-panel && docker compose logs -f panel    # логи
```

Прежде чем что-то менять, скрипт проверяет, что домен указывает на публичный IP этого сервера, порты 80 и 443 свободны, а каталог установки пригоден. Если проверка не прошла, в терминале скрипт предложит повторить, продолжить или выйти, а без терминала остановится (`--skip-preflight` пропускает проверки). Файрвол скрипт не трогает, порты 80 и 443 откройте сами. Все флаги перечислены в `install.sh --help`, и у каждого есть переменная окружения `TGWP_<ИМЯ>`. Опубликованный образ собран для `linux/amd64` и `linux/arm64`.

### Вручную через docker compose

```bash
git clone <ваш-репозиторий> tgproxy-web && cd tgproxy-web/deploy
cp ../.env.example .env
```

Заполните секреты и домен в `deploy/.env`:

```bash
# три секрета
printf 'MASTER_KEY=%s\n'     "$(openssl rand -base64 32)"
printf 'SESSION_SECRET=%s\n' "$(openssl rand -base64 32)"
printf 'METRICS_TOKEN=%s\n'  "$(openssl rand -hex 32)"
```

Впишите полученные значения в соответствующие строки `.env`, затем задайте:

```
PANEL_PUBLIC_URL=https://panel.example.com
PANEL_DOMAIN=panel.example.com
ACME_EMAIL=admin@example.com
```

В compose-варианте `DATABASE_URL` задаёт сам `docker-compose.yml` (сервис `postgres`), так что строку в `.env` можно оставить как есть.

Запуск:

```bash
docker compose up -d --build postgres panel caddy
docker compose logs -f panel        # ждём строку "panel listening"
```

Создайте первого администратора (роль `owner`):

```bash
docker compose exec panel /app/panel admin create root 'надёжный-пароль'
```

Откройте `https://panel.example.com` и войдите.

![Вход](screenshots/ru/login.png)

Что важно знать:

- `MASTER_KEY` шифрует секреты ключей и токены в базе. Потеряете ключ — потеряете все секреты, поэтому храните копию вне сервера.
- `METRICS_TOKEN` обязателен. Без него панель не стартует, потому что `/metrics` доступен на публичном домене.
- Данные лежат в томах `pgdata`, `paneldata`, `caddydata`. Не удаляйте их командой `down -v` на проде.

## 3. Вариант B: локально без домена

Чтобы попробовать панель на своей машине, её можно открыть напрямую на `:8080`, без Caddy и TLS.

Установщиком: `curl -fsSL https://raw.githubusercontent.com/greenpandorik/tgproxy-panel/main/install.sh | sudo bash -s -- --local --yes` (Linux, root). Вручную из checkout:

```bash
cd deploy
cp ../.env.example .env
# заполните MASTER_KEY, SESSION_SECRET, METRICS_TOKEN как выше; PANEL_PUBLIC_URL=http://localhost:8080
docker compose -f docker-compose.yml -f docker-compose.override.example.yml up -d --build postgres panel
docker compose exec panel /app/panel admin create root 'change-me-now-1'
```

Панель доступна на `http://localhost:8080`. Настоящие серверы к такой панели не подключить, потому что агенту нужен публичный адрес панели, но интерфейс, ключи и шаблоны работают полностью.

Чтобы увидеть интерфейс с тестовой сервером и настоящим relay, поднимите демо-сервер в контейнере:

```bash
make e2e     # собирает образы, поднимает panel + fakenode, прогоняет сквозной smoke и гасит стенд
```

```bash

Для фронтенда с горячей перезагрузкой запустите `cd web && npm run dev` (dev-сервер проксирует `/api` на `:8080`).

Проверки перед изменениями:

```

## 6. Подключение сервера

Подготовьте VPS: A-запись домена сервера на её IP, открытые порты 80 и 443, и ничего не должно их слушать.

**A-запись должна указывать на сервер ещё до запуска команды установки.** Скрипт проверяет это раньше, чем что-либо ставит. Его первый шаг, «Pre-flight checks», печатает по строке на проверку:

- `arch` (x86_64), `systemd` и `panel` (панель отвечает на `/healthz` с этого хоста).
- `public_ip`, публичный IPv4 этого сервера. Это `TGWP_PUBLIC_IP`, если он задан, иначе `public_ip` сервера в панели, иначе один из двух найденных кандидатов: адрес исходящего интерфейса или адрес, который видит `api.ipify.org`. Побеждает тот, на который уже указывает A-запись, а если ни тот ни другой, то адрес интерфейса, когда он публичный. Если адреса различаются, печатаются оба: на NAT-хосте адрес egress провайдера — как раз тот, на котором ничего не слушает.
- `dns`: A-запись сервера указывает на этот адрес.
- На сервере с telemt `tls_domain` (резолвится; только предупреждение).
- `ports`: 80, 443 и порт Fake-TLS свободны. Caddy или telemt, оставшиеся от прошлого запуска этого же скрипта, не мешают.

Провал `arch`, `systemd`, `panel` или `public_ip` останавливает скрипт. Провал `dns` или `ports` показывает меню, которое читается с терминала:

```
  What now?  [r] re-run the checks   [c] continue anyway   [q] quit
```

Поправьте запись в другом окне и нажмите `r`; `q` (или Ctrl-C) выходит, ничего не установив. Если терминала нет (облачная консоль, которая просто прогоняет скрипт), скрипт выходит так же. Чтобы всё равно продолжить, запустите `curl … | sudo TGWP_SKIP_PREFLIGHT=1 bash`. `TGWP_DRY_RUN=1` останавливает скрипт сразу после проверок.

После пакетов установщик поднимает Caddy и до 120 секунд ждёт, пока `https://<домен сервера>/` ответит с валидным сертификатом. Сервер с telemt затем до 60 секунд ждёт, пока telemt сообщит о готовности по control API. Только после этого скрипт регистрирует сервер в панели. Регистрация — единственный шаг, который тратит одноразовый токен установки. Если скрипт упал раньше шага «Registration» (обычно на ожидании сертификата), устраните причину и запустите ту же команду ещё раз: уже поставленные пакеты переиспользуются. Сообщение об ошибке заканчивается последними 30 строками `journalctl -u caddy` (или `-u telemt`) и подсказывает, что проверить. Caddy должен получить сертификат до запуска telemt, потому что telemt снимает TLS-отпечаток своего `tls_domain` настоящим хендшейком на 443 и не активирует новую конфигурацию, пока отпечатка нет.

В панели откройте «Серверы → Добавить сервер». Укажите имя, домен сервера и e-mail для сертификата Let's Encrypt.

![Создание сервера](screenshots/ru/node-create-dialog.png)

Панель выдаст одноразовую команду установки. Токен действует 24 часа.

![Команда установки](screenshots/ru/node-install-dialog.png)

Выполните команду на VPS от root:

```bash
curl -fsSL https://panel.example.com/api/v1/install/<token>.sh | sudo bash
```

В зависимости от движка сервера скрипт ставит telemt (по умолчанию) или `tproxy-server` (закреплённый коммит) с официальным MTProxy, а также Caddy и агента. Он получает сертификат и регистрирует сервер, и через минуту сервер появляется как онлайн.

Для обоих движков скрипт также записывает `/etc/sysctl.d/90-tgwp.conf` с сетевыми настройками для прокси-сервера, взятыми из MTPROTO_FIX_By_MEKO: BBR с планировщиком `fq`, увеличенные очереди accept и SYN (`somaxconn`, `tcp_max_syn_backlog`, `netdev_max_backlog` = 65535), TCP Fast Open и короткие keepalive (45/15 с × 3 пробы), чтобы мёртвые клиенты отваливались примерно за минуту. Если ядро не принимает какой-то ключ (в контейнере или на старом ядре), скрипт пишет об этом и продолжает установку. Файл можно спокойно удалить: от него зависят только эти значения.

Отдельная строка «Постквантовый обмен ключами» носит информационный характер. Она показывает, договаривается ли Caddy на сервере о гибридном X25519MLKEM768 с современными клиентами, и не влияет на общий результат проверки.

На сервере с tproxy каждое применение перезапускает relay, и клиенты сами переподключаются; сервер с telemt применяет изменения без перезапуска (см. следующий раздел).

## 7. Движок сервера: telemt или tproxy

Движок выбирается при создании сервера и потом не меняется. Чтобы перевести сервер на другой движок, её нужно переустановить.

**`telemt` (по умолчанию).** Один процесс telemt закреплённой версии плюс Caddy:

- Caddy из подписанного репозитория проекта Caddy держит TLS на 443 и проксирует на loopback-листенер telemt (`X-Forwarded-For`). Сайт-прикрытие отдаёт сам telemt (decoy), Caddy ничего не отдаёт. Поэтому запрос без валидного секрета обрабатывает тот же процесс, что и проксируемый.
- Бинарник telemt версии `TELEMT_VERSION` из релизов проекта. Его sha256 сверяется с `TELEMT_SHA256_X86_64` до установки в `/usr/local/bin/telemt`.
- Системная учётка `telemt`, юнит работает без root.
- `tgwp-agent init-node --engine telemt` пишет `/etc/telemt/telemt.toml`, токен control API в `/etc/telemt/api.token` (0600), юнит `/etc/systemd/system/telemt.service` и сайт-прикрытие в `/var/lib/telemt/public`.
- Таблица nftables `tgwp_telemt`, закрывающая внутренние порты снаружи.

**`tproxy`.** Старый стек: `tproxy-server` закреплённого коммита, официальный MTProxy, Caddy и агент. Его ставит апстримный `deploy/install.sh`.

Порты на сервере с telemt: **80 и 443 наружу** (Caddy, ACME, WEB-транспорт), **`classic_port` наружу** (Fake-TLS, по умолчанию 8443) и **9090 (метрики), 9091 (control API), 18080 (WEB-листенер) только на loopback**. На сервере с tproxy наружу смотрят только 80 и 443.

Сервер также должен доставать **свой собственный публичный адрес на 443**. Неизвестный SNI на Fake-TLS-порту маскируется в `tls_domain:443`, а это IP самого сервера. Там, где NAT-hairpin или egress-политика не дают хосту подключиться к своему публичному адресу, маскировка ломается без всяких сообщений: проба получает ошибку соединения вместо сайта-прикрытия, то есть ровно тот отпечаток, которого схема должна избегать. `curl -sSI https://<домен сервера>/` **с самого сервера** должен вернуть ответ сайта-прикрытия.

Карточка «Адреса и Fake-TLS» на странице сервера позволяет поправить `public_ip` после установки (на NAT-хосте установщик может зарегистрировать адрес egress вместо адреса интерфейса). Следующее применение перепишет адрес WEB-вхоста в конфиге telemt и перезапустит telemt, ссылки не пострадают. Изменение `tls_domain` или `classic_port` на той же карточке — единственное действие в панели, которое и перезапускает telemt, *и* ломает ссылки. Следующее применение перепишет конфиг сервера и перезапустит процесс, активные соединения разорвутся, и **все выданные для этого сервера Fake-TLS-ссылки перестанут работать**, потому что домен и порт зашиты в секрет ссылки. Выдайте ссылки заново. WEB-ссылки не меняются.

На той же карточке есть **запасные домены маскировки**. Каждый домен из списка даёт каждому ключу ещё одну Fake-TLS-ссылку, основная ссылка при этом не меняется. Если провайдер начнёт резать основной домен по SNI, пользователь просто возьмёт ссылку с другим доменом, переустанавливать сервер не нужно. Сохранение перезапускает telemt, но уже выданные ссылки продолжают работать. Подходят только настоящие сайты, которые отвечают по HTTPS на 443 и доступны с сервера: telemt при старте снимает TLS-отпечаток каждого домена, и если один недоступен, применение откатится. Нужен агент 2.9.2 или новее, до восьми доменов на сервер.

Что это меняет в панели:

- **Две ссылки на ключ.** На сервере с telemt ключ отдаёт и WEB-ссылку (`https://t.me/webproxy?server=…`), и Fake-TLS (`https://t.me/proxy?server=…&port=<classic_port>&secret=ee…`). На сервере с tproxy только WEB.
- **Лимиты ключа** (квота трафика, скорость вверх и вниз, максимум уникальных IP, максимум соединений) работают только на telemt, их применяет сам telemt. На серверах с tproxy поля показаны как недоступные.
- **Применение без перезапуска.** На сервере с telemt изменения профилей уходят в control API, и живые сессии не рвутся. На сервере с tproxy каждое применение перезапускает relay.
- **Версия telemt закреплена.** Установочный скрипт скачивает и проверяет то, что указано в `TELEMT_VERSION` и `TELEMT_SHA256_X86_64` в `.env`. Меняйте их только парой. Уже установленные серверы переводятся на новую версию командой `tgwp-agent upgrade` на самом сервере, об этом ниже.

Локальный демо-стенд с настоящим бинарником telemt, без VPS и без Telegram-клиента:

```bash
make e2e-telemt
```

Стенд поднимает postgres и панель, собирает образ `deploy/Dockerfile.fakenode-telemt` (telemt из релиза, контрольная сумма проверяется), создаёт сервер с telemt и ключ с лимитами и проверяет, что telemt на «серверу» действительно получил пользователя через control API. `make e2e` делает то же самое для движка tproxy.

### Обновление сервера

Сервер обновляется сам. Когда в панели меняется закреплённая версия telemt (вы обновили панель или сами поменяли `TELEMT_VERSION`/`TELEMT_SHA256_X86_64` в `.env`), зайдите на сервер по ssh под root и выполните:

```bash
tgwp-agent upgrade --check   # что изменится; ничего не меняет
tgwp-agent upgrade           # покажет план и спросит подтверждение
tgwp-agent upgrade --yes     # без вопросов; обязателен, если нет терминала
```

Команда берёт токен, который у сервера уже лежит в `/etc/tgwp-agent/agent.env`, и спрашивает панель, что на сервере должно стоять. Поэтому **не нужно** генерировать команду установки в панели и переустанавливать сервер целиком. Обновляется только то, что отличается: бинарник telemt, бинарник агента или оба (`--telemt` / `--agent` сужают область). Каждая загрузка проверяется по sha256 из панели **до** того, как что-либо будет заменено. Предыдущий бинарник сохраняется, юнит перезапускается, и команда ждёт, пока он не отчитается о готовности. Если не отчитался, возвращается предыдущий бинарник, и юнит перезапускается с ним. Перезапуск telemt рвёт живые сессии на сервере, поэтому обновляйте серверы по одному.

На хосте панели `sudo /opt/tgproxy-panel/install.sh --update` заодно переносит пины telemt в `.env` на те, что идут с новым релизом панели. Обычный порядок такой: сначала обновить панель, затем выполнить `tgwp-agent upgrade` на каждом сервере.

## 9. Сайт-прикрытие сервера

На домене сервера должен работать обычный сайт. В разделе «Сайты-прикрытия» можно посмотреть
любой из 15 встроенных сайтов, отредактировать копию или импортировать статический ZIP с
`index.html`. Назначьте сайт из галереи или с вкладки «Сайт» на странице сервера и дождитесь
применения. Сервер с telemt, который это поддерживает, может брать сайт с локального или
приватного HTTP upstream. После назначения проверьте публичный корень сайта, ресурсы и WEB
proxy: предпросмотр в редакторе не показывает, что развернулось на сервере.

При создании сервера мастер сначала спрашивает реквизиты, DNS и параметры прокси и только потом
выдаёт команду установки. Диалог установки следит за тем, как агент подключается и становится
готов, а после подключения предлагает диагностику. Сервер появится, только когда вы выполните
команду на сервере: запись в панели ещё не установка.
Вкладка «WEB» показывает состояние runtime и транспортов и поддерживаемые настройки.
Диагностика хранит историю и экспортирует JSON, а непроведённая проверка не засчитывается
как пройденная. Карточка обновления Telemt ставит закреплённую панелью версию и показывает
ход выполнения и итог восстановления. См. [runbook](runbook.md).

![Шаблоны](screenshots/ru/sites.png)

Редактор проверяет ограничения relay (никаких внешних ресурсов, inline-обработчиков и форм) и выносит стили и скрипты в файлы. При назначении каждый сервер получает уникализированную копию со своим порядком блоков и своими именами классов и файлов, чтобы у серверов не было общей сигнатуры.

## 12. Резервные копии, ротация ключа, обновление

Бэкапы: «Настройки → Резервные копии → Создать копию» или расписание (час по UTC и сколько копий хранить). Файлы лежат в томе панели в `/data/backups/`.

![Резервные копии](screenshots/ru/settings-backups.png)

Восстановление из копии (панель должна быть остановлена):

```bash
docker compose stop panel
docker compose run --rm panel db restore /data/backups/<файл>.dump --yes
docker compose start panel
```

Ротация `MASTER_KEY`:

```bash
docker compose stop panel
# в .env добавьте MASTER_KEY_NEW=<новый ключ base64>
docker compose run --rm panel keys rotate --dry-run
docker compose run --rm panel keys rotate
# затем в .env: MASTER_KEY=<новый>, MASTER_KEY_VERSION=2, MASTER_KEY_V1=<старый>; MASTER_KEY_NEW удалить
docker compose start panel
```

Обновление панели, поставленной установщиком:

```bash
sudo /opt/tgproxy-panel/install.sh --update      # последний релиз; --version 1.2.0 для конкретного
```

Обновление панели, собранной из checkout:

```bash
git pull
cd deploy && docker compose up -d --build panel
```

Обновление relay на серверах: агента панель раздаёт сама, а `tproxy-server` закреплён на коммите из `TPROXY_COMMIT`. Чтобы сменить коммит, сервер нужно переустановить новой командой установки.

## 13. Переменные окружения

| Переменная | Назначение |
|---|---|
| `DATABASE_URL` | Строка подключения к PostgreSQL |
| `MASTER_KEY`, `MASTER_KEY_VERSION` | Ключ шифрования секретов в базе и его версия |
| `SESSION_SECRET` | Подпись cookie сессий |
| `PANEL_PUBLIC_URL` | Публичный адрес панели, попадает в команду установки серверов |
| `PANEL_HTTP_ADDR` | Адрес прослушивания внутри контейнера, обычно `:8080` |
| `NODE_DRIVER` | `gateway` для реальных серверов, `mock` для демо и тестов |
| `METRICS_TOKEN` | Токен для `/metrics`, обязателен при `gateway` |
| `TPROXY_COMMIT` | Коммит `tproxy-server` для установки серверов |
| `FEATURE_TOTP` | Включает 2FA |
| `APPLY_INTERVAL`, `OFFLINE_AFTER` | Интервал батча применения и порог офлайна, секунды |
| `PANEL_DOMAIN`, `ACME_EMAIL` | Только для Caddy в compose |

## 14. Если что-то не работает

- Панель не стартует: `docker compose logs panel`. Чаще всего причина в пустом `METRICS_TOKEN` или неверном `DATABASE_URL`.
- Сервер не появляется онлайн: на VPS выполните `systemctl status tgwp-agent tproxy-server mtproxy caddy` и `journalctl -u tgwp-agent -n 100`. Агент должен достучаться до `PANEL_PUBLIC_URL`.
- Ключ висит в статусе «ожидает»: сервер офлайн или применение упало. Посмотрите блок «История применений» на вкладке «Обслуживание» сервера, там лог агента.
- Подробные сценарии: [runbook.md](runbook.md).

Первую боевую установку сделайте на тестовом VPS и проверьте подключение из Telegram Desktop, прежде чем раздавать ключи.
