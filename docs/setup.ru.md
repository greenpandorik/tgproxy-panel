# Установка и запуск панели

English version: [setup.en.md](setup.en.md)

Панель управления Telegram WEB Proxy: один Go-бинарь с встроенным веб-интерфейсом, PostgreSQL и Caddy для TLS. Панель ставится на отдельный сервер и управляет нодами, на которых работает официальный `tproxy-server` + MTProxy. Все скриншоты ниже сняты с демо-данными.

![Дашборд](screenshots/dashboard.png)

## 1. Что понадобится

| Компонент | Требование |
|---|---|
| Сервер панели | Linux с Docker и Docker Compose v2, 1 CPU / 1 GB достаточно; домен с A-записью на этот сервер; открытые порты 80 и 443 |
| Каждая нода | Отдельный VPS: Ubuntu 22.04+ или Debian 12+, x86_64, публичный IPv4, свой домен (A-запись), root или sudo, открытые 80 и 443 |
| Для разработки без Docker | Go 1.26+, Node 22+, PostgreSQL 16 |

Ноды и панель должны быть на разных хостах: relay на ноде занимает порты 80/443.

## 2. Вариант A: сервер с доменом (рекомендуется)

Панель работает за Caddy, который сам получает сертификат Let's Encrypt.

```bash
git clone <ваш-репозиторий> tgproxy-web && cd tgproxy-web/deploy
cp ../.env.example .env
```

Заполните секреты и домен в `deploy/.env`:

```bash
# три секрета
printf 'MASTER_KEY=%s\n'     "$(openssl rand -base64 32)"
printf 'SESSION_SECRET=%s\n' "$(openssl rand -base64 32)"
printf 'METRICS_TOKEN=%s\n'  "$(openssl rand -hex 32)"
```

Впишите полученные значения в соответствующие строки `.env`, затем задайте:

```
PANEL_PUBLIC_URL=https://panel.example.com
PANEL_DOMAIN=panel.example.com
ACME_EMAIL=admin@example.com
```

`DATABASE_URL` в compose-варианте задаётся самим `docker-compose.yml` (сервис `postgres`), строку в `.env` можно оставить как есть.

Запуск:

```bash
docker compose up -d --build postgres panel caddy
docker compose logs -f panel        # ждём строку "panel listening"
```

Создайте первого администратора (роль `owner`):

```bash
docker compose exec panel /app/panel admin create root 'надёжный-пароль'
```

Откройте `https://panel.example.com` и войдите.

![Вход](screenshots/login.png)

Что важно знать:

- `MASTER_KEY` шифрует секреты ключей и токены в базе. Потеря ключа означает потерю всех секретов, храните его вне сервера.
- `METRICS_TOKEN` обязателен: без него панель не стартует, потому что `/metrics` доступен на публичном домене.
- Данные лежат в томах `pgdata`, `paneldata`, `caddydata`. Не удаляйте их командой `down -v` на проде.

## 3. Вариант B: локально без домена

Для проверки на своей машине панель открывается напрямую на `:8080`, без Caddy и TLS.

```bash
cd deploy
cp ../.env.example .env
# заполните MASTER_KEY, SESSION_SECRET, METRICS_TOKEN как выше; PANEL_PUBLIC_URL=http://localhost:8080
docker compose -f docker-compose.yml -f docker-compose.override.example.yml up -d --build postgres panel
docker compose exec panel /app/panel admin create root 'change-me-now-1'
```

Панель доступна на `http://localhost:8080`. Реальные ноды к такой панели подключить нельзя (агент должен достучаться до панели по публичному адресу), но интерфейс, ключи и шаблоны можно посмотреть целиком.

Чтобы увидеть интерфейс с тестовой нодой и настоящим relay, поднимите демо-ноду в контейнере:

```bash
make e2e     # собирает образы, поднимает panel + fakenode, прогоняет сквозной smoke и гасит стенд
```

## 4. Вариант C: разработка без Docker

```bash
brew install postgresql@16 && brew services start postgresql@16   # macOS
createuser -s tgwp && psql -d postgres -c "ALTER USER tgwp PASSWORD 'tgwp'"
createdb -O tgwp tgwp && createdb -O tgwp tgwp_test

cp .env.example .env         # заполните MASTER_KEY, SESSION_SECRET; NODE_DRIVER=mock позволяет не задавать METRICS_TOKEN
make tools                   # sqlc, gofumpt, golangci-lint, protoc-плагины
make web                     # сборка SPA в web/dist (встраивается в бинарь)
go run ./cmd/panel admin create root 'change-me-now-1'
make run                     # панель на :8080
```

Для фронтенда с горячей перезагрузкой: `cd web && npm run dev` (dev-сервер проксирует `/api` на `:8080`).

Проверки перед изменениями:

```bash
make test                    # go test -p 1 ./... (тесты делят одну базу, поэтому -p 1)
make lint
cd web && npm run typecheck && npm run lint && npm run test -- --run && npm run i18n:check
```

## 5. Первый вход и двухфакторная защита

Сразу после входа смените пароль: Настройки → Безопасность. Смена пароля завершает все остальные сессии.

Чтобы включить 2FA, установите `FEATURE_TOTP=true` в `.env` и перезапустите панель. В той же вкладке появится раздел с QR-кодом для приложения-аутентификатора.

![Безопасность](screenshots/settings-security.png)

![Подключение аутентификатора](screenshots/settings-2fa-enrol.png)

После подтверждения кода панель покажет восемь резервных кодов один раз. Сохраните их. Если доступ к аутентификатору потерян, владелец сбрасывает 2FA с сервера:

```bash
docker compose exec panel /app/panel admin totp-reset <логин>
```

## 6. Подключение ноды

Подготовьте VPS: A-запись домена ноды на её IP, открытые 80 и 443, ничего не должно слушать эти порты.

**A-запись должна уже указывать на ноду до запуска команды установки.** На telemt-ноде установщик сначала поднимает Caddy и до 120 секунд ждёт, пока `https://<домен ноды>/` ответит с валидным сертификатом; без DNS Caddy не получит сертификат от Let's Encrypt, и установщик завершится с ошибкой и последними 30 строками `journalctl -u caddy` — вместо ноды, у которой потом падает каждое применение. (telemt снимает TLS-отпечаток своего `tls_domain` настоящим хендшейком на 443 и не активирует новую конфигурацию, пока его нет.)

В панели: Ноды → Добавить ноду. Укажите имя, домен ноды и e-mail для сертификата Let's Encrypt.

![Создание ноды](screenshots/node-create-dialog.png)

Панель выдаст одноразовую команду установки. Токен действует 24 часа.

![Команда установки](screenshots/node-install-dialog.png)

Выполните команду на VPS от root:

```bash
curl -fsSL https://panel.example.com/api/v1/install/<token>.sh | sudo bash
```

Скрипт ставит `tproxy-server` (закреплённый коммит), официальный MTProxy, Caddy, агента, получает сертификат и регистрирует ноду. Через минуту нода появится как онлайн.

Вместе с зависимостями скрипт (для обоих движков) записывает `/etc/sysctl.d/90-tgwp.conf` — сетевые настройки для прокси-ноды, взятые из MTPROTO_FIX_By_MEKO: BBR с планировщиком `fq`, увеличенные очереди accept/SYN (`somaxconn`, `tcp_max_syn_backlog`, `netdev_max_backlog` = 65535), TCP Fast Open и короткие keepalive (45/15 с × 3 пробы), чтобы мёртвые клиенты отваливались примерно за минуту. Если ядро не принимает какой-то ключ (контейнер, старое ядро), скрипт пишет об этом и продолжает установку. Файл можно безопасно удалить — ничего, кроме этих значений, от него не зависит.

![Список нод](screenshots/nodes.png)

На странице ноды видны состояние служб, ресурсы, проверка готовности (DNS, порты, сертификат, ответ сайта; на telemt-ноде ещё и маскировка Fake-TLS), профили, логи и статистика relay. Отдельная строка «Постквантовый обмен ключами» — информационная: она показывает, договаривается ли Caddy на ноде гибридный X25519MLKEM768 с современными клиентами, и не влияет на общий результат проверки.

![Карточка ноды](screenshots/node-detail.png)

Изменения профилей и сайта применяются не сразу, а батчем воркера раз в `APPLY_INTERVAL` секунд (по умолчанию 45) или кнопкой «Применить». Каждое применение перезапускает relay, и активные подключения пересоздаются клиентами автоматически.

## 7. Движок ноды: telemt или tproxy

Движок выбирается при создании ноды и после этого не меняется — переезд на другой движок означает переустановку ноды.

**`telemt` (по умолчанию).** Один процесс telemt закреплённой версии плюс Caddy:

- Caddy из подписанного репозитория проекта Caddy держит TLS на 443 и проксирует на loopback-листенер telemt (`X-Forwarded-For`). Сайт-заглушку отдаёт сам telemt (decoy), а не Caddy: запрос без валидного секрета обрабатывает тот же процесс, что и проксируемый.
- Бинарник telemt версии `TELEMT_VERSION` из релизов проекта, sha256 сверяется с `TELEMT_SHA256_X86_64` до установки в `/usr/local/bin/telemt`.
- Системная учётка `telemt`, юнит работает без root.
- `tgwp-agent init-node --engine telemt` пишет `/etc/telemt/telemt.toml`, токен control API в `/etc/telemt/api.token` (0600), юнит `/etc/systemd/system/telemt.service` и сайт-заглушку в `/var/lib/telemt/public`.
- Таблица nftables `tgwp_telemt`, закрывающая внутренние порты снаружи.

**`tproxy`.** Старый стек: `tproxy-server` закреплённого коммита, официальный MTProxy, Caddy и агент — ставится апстримным `deploy/install.sh`.

Порты на telemt-ноде: **80 и 443 наружу** (Caddy, ACME, WEB-транспорт), **`classic_port` наружу** (Fake-TLS, по умолчанию 8443) и **9090 (метрики), 9091 (control API), 18080 (WEB-листенер) только на loopback**. На tproxy-ноде наружу смотрят только 80 и 443.

Нода также должна доставать **свой собственный публичный адрес на 443**: неизвестный SNI на Fake-TLS-порту маскируется в `tls_domain:443`, а это IP самой ноды. Там, где NAT-hairpin или egress-политика запрещают хосту подключаться к своему публичному адресу, маскировка молча ломается — проба получает ошибку соединения вместо сайта-прикрытия, то есть ровно тот отпечаток, которого схема и должна избегать. `curl -sSI https://<домен ноды>/` **с самой ноды** должен вернуть ответ сайта-прикрытия.

Изменение `tls_domain` или `classic_port` на странице ноды — единственное действие в панели, которое перезапускает telemt: следующее применение перепишет конфиг ноды и перезапустит процесс, активные соединения разорвутся, и **все выданные для этой ноды Fake-TLS-ссылки перестанут работать** — домен и порт зашиты в секрет ссылки, поэтому ссылки нужно выдать заново. WEB-ссылки не меняются.

Что это меняет в панели:

- **Две ссылки на ключ.** На telemt-ноде ключ отдаёт и WEB-ссылку (`https://t.me/webproxy?server=…`), и Fake-TLS (`https://t.me/proxy?server=…&port=<classic_port>&secret=ee…`). На tproxy-ноде только WEB.
- **Лимиты ключа** (квота трафика, скорость вверх/вниз, максимум уникальных IP, максимум соединений) работают только на telemt: их применяет сам telemt. На tproxy-нодах поля показываются как недоступные.
- **Применение без перезапуска.** Изменения профилей на telemt-ноде уходят в control API, живые сессии не рвутся. На tproxy-ноде каждое применение перезапускает relay.
- **Версия telemt закреплена.** `TELEMT_VERSION` и `TELEMT_SHA256_X86_64` в `.env` — это то, что скачает и проверит установочный скрипт. Меняйте их только парой; апгрейд ноды на новую версию — повторный запуск установки (см. runbook).

Локальный демо-стенд с настоящим бинарником telemt (без VPS и без Telegram-клиента):

```bash
make e2e-telemt
```

Поднимает postgres + панель, собирает образ `deploy/Dockerfile.fakenode-telemt` (телемт из релиза, sha проверяется), создаёт telemt-ноду, ключ с лимитами и проверяет, что telemt на «ноде» действительно получил пользователя через control API. `make e2e` делает то же самое для движка tproxy.

![Ссылка и QR](screenshots/key-link-dialog.png)

## 12. Резервные копии, ротация ключа, обновление

Бэкапы: Настройки → Резервные копии → «Создать резервную копию» или расписание (час по UTC, сколько копий хранить). Файлы лежат в томе панели в `/data/backups/`.

![Резервные копии](screenshots/settings-backups.png)

Восстановление из копии (панель должна быть остановлена):

```bash
docker compose stop panel
docker compose run --rm panel db restore /data/backups/<файл>.dump --yes
docker compose start panel
```

Ротация `MASTER_KEY`:

```bash
docker compose stop panel
# в .env добавьте MASTER_KEY_NEW=<новый ключ base64>
docker compose run --rm panel keys rotate --dry-run
docker compose run --rm panel keys rotate
# затем в .env: MASTER_KEY=<новый>, MASTER_KEY_VERSION=2, MASTER_KEY_V1=<старый>; MASTER_KEY_NEW удалить
docker compose start panel
```

Обновление панели:

```bash
git pull
cd deploy && docker compose up -d --build panel
```

Обновление relay на нодах: панель раздаёт агента сама, а `tproxy-server` закреплён на коммите из `TPROXY_COMMIT`. Смена коммита требует переустановки ноды новой командой установки.

## 13. Переменные окружения

| Переменная | Назначение |
|---|---|
| `DATABASE_URL` | Строка подключения к PostgreSQL |
| `MASTER_KEY`, `MASTER_KEY_VERSION` | Ключ шифрования секретов в базе и его версия |
| `SESSION_SECRET` | Подпись cookie сессий |
| `PANEL_PUBLIC_URL` | Публичный адрес панели, попадает в команду установки нод |
| `PANEL_HTTP_ADDR` | Адрес прослушивания внутри контейнера, обычно `:8080` |
| `NODE_DRIVER` | `gateway` для реальных нод, `mock` для демо и тестов |
| `METRICS_TOKEN` | Токен для `/metrics`, обязателен при `gateway` |
| `TPROXY_COMMIT` | Коммит `tproxy-server` для установки нод |
| `FEATURE_TOTP` | Включает 2FA |
| `APPLY_INTERVAL`, `OFFLINE_AFTER` | Интервал батча применения и порог офлайна, секунды |
| `PANEL_DOMAIN`, `ACME_EMAIL` | Только для Caddy в compose |

## 14. Если что-то не работает

- Панель не стартует: `docker compose logs panel`. Чаще всего пустой `METRICS_TOKEN` или неверный `DATABASE_URL`.
- Нода не появляется онлайн: на VPS `systemctl status tgwp-agent tproxy-server mtproxy caddy` и `journalctl -u tgwp-agent -n 100`. Агент должен достучаться до `PANEL_PUBLIC_URL`.
- Ключ висит в «ожидает»: нода офлайн или применение упало. Смотрите вкладку «Обзор» ноды, блок «Последние применения», там лог агента.
- Подробные сценарии: [runbook.md](runbook.md).

Что ещё не проверялось на реальном железе: установочный скрипт ноды и путь агента через Caddy прогонялись только на контейнерной демо-ноде. Первую боевую установку делайте на тестовом VPS и проверьте подключение из Telegram Desktop.
