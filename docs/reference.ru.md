## Как это работает

Система состоит из двух частей: панели и прокси-серверов.

Панель — это одна программа на Go со встроенным веб-интерфейсом. Она работает в Docker на
отдельном сервере, рядом с базой PostgreSQL, где хранится всё: серверы, пользователи, сайты,
настройки и история. Перед панелью стоит Caddy, он получает для неё HTTPS-сертификат.

На каждом прокси-сервере работают движок прокси и небольшая программа-агент `tgwp-agent`.
Движок принимает подключения пользователей Telegram: на новых серверах это telemt, на старых
может быть связка tproxy (см. [Движки серверов](#движки-серверов)). Агент выполняет на сервере
команды панели и сообщает ей о состоянии.

```
браузер администратора ──HTTPS──> Caddy ──> панель ──> PostgreSQL
                                              ▲
                                              │ gRPC, соединение открывает агент
                                              │
прокси-сервер:  tgwp-agent ──> telemt: WEB-прокси за Caddy на 443, Fake-TLS на 8443,
                               сайт-прикрытие, API управления на 127.0.0.1:9091
         или:   tgwp-agent ──> tproxy-server + MTProxy, Caddy на 443
```

Соединение с панелью агент открывает сам и держит его открытым. Панель никогда не подключается
к серверу, поэтому серверу нужны только выход в интернет и собственные публичные порты. Если
соединение рвётся, агент подключается снова, выжидая перед каждой попыткой от 1 до 30 секунд.

Раз в 30 секунд агент присылает сигнал о жизни: состояние служб и нагрузку. Кроме того, раз в
минуту панель собирает статистику с каждого сервера на связи. У сервера один из четырёх
статусов:

| Статус | Что значит |
|---|---|
| `pending` | Сервер добавлен в панель, но его агент ещё не подключался |
| `online` | Агент на связи, службы отвечают |
| `degraded` | Агент отвечает, но какая-то служба на сервере готова не полностью |
| `offline` | Сигналов нет дольше `OFFLINE_AFTER` секунд (по умолчанию 90) |

### Как изменение попадает на сервер

Когда вы создаёте, выключаете или отзываете пользователя, меняете лимиты или назначаете
сайт-прикрытие, панель сохраняет изменение и отмечает затронутые серверы как ожидающие
применения. Каждые `APPLY_INTERVAL` секунд (по умолчанию 45) фоновая задача отправляет на каждый
такой сервер полную конфигурацию. Оба интервала можно поменять и без перезапуска: «Настройки» →
«Уведомления». Кнопка «Применить изменения» на странице сервера отправляет изменения сразу.

Одновременно фоновые применения выполняются максимум на четырёх серверах. После ошибки той же
версии настроек пауза между повторными попытками растёт от 45 секунд до 15 минут со случайным
разбросом. Новая правка, в том числе отзыв пользователя, не наследует паузу предыдущей версии;
ручное применение также доступно сразу. Остальные серверы остаются в очереди.

На сервере с telemt агент применяет изменения через API управления telemt, и подключённые люди
ничего не замечают. На сервере с tproxy агент переписывает файлы relay и перезапускает его:
действующие соединения рвутся, клиенты Telegram переподключаются сами. Новый пользователь
начинает работать после применения, обычно в течение минуты.

Если применение не удалось, агент возвращает прежнюю конфигурацию. Как разобрать такую
операцию, написано в [руководстве по эксплуатации](runbook.ru.md#изменения-не-доходят-до-сервера).

Кроме того, раз в минуту панель находит пользователей, у которых истёк срок, и снимает их с
серверов. Такой пользователь не отзывается: если продлить срок, доступ вернётся.

## Движки серверов

Движок — это программа прокси на сервере. Его выбирают при добавлении сервера, и потом поменять
его нельзя. По умолчанию стоит telemt, для новых серверов берите его.

| | telemt | tproxy |
|---|---|---|
| Прямые ссылки пользователя | WEB и Fake-TLS, плюс ещё одна Fake-TLS-ссылка на каждый запасной домен маскировки | Только WEB |
| Лимиты пользователя: трафик, скорость, уникальные IP, соединения | Есть, их соблюдает telemt | Нет |
| Трафик по пользователям | Есть | Нет |
| Применение изменений | Без перезапуска | С перезапуском relay |
| Публичные порты | 80, 443 и порт Fake-TLS (по умолчанию 8443) | 80 и 443 |
| Задержка до датацентров Telegram | Есть | Нет |
| Вкладка «Настройки», полная проверка сервера, данные WEB-транспорта | Есть | Нет |
| Обновление Telemt из панели | Есть | Нет |

### telemt

Один процесс telemt обслуживает WEB-прокси, Fake-TLS, сайт-прикрытие и API управления, через
который с ним работает агент. Скрипт установки сервера ставит:

- Caddy из релиза на GitHub, версию и sha256 закрепляет панель. Он держит сертификат на порту 443 и
  передаёт запросы WEB-слушателю telemt на `127.0.0.1:18080`, добавляя `X-Forwarded-For`.
  Сам Caddy файлов не отдаёт. Сайт-прикрытие показывает telemt, поэтому посетителю без
  действующего ключа отвечает тот же процесс, что и пользователю прокси.
- Релиз telemt, указанный в `TELEMT_VERSION`. Он скачивается с
  `https://github.com/telemt/telemt/releases` и сверяется с `TELEMT_SHA256_X86_64`, прежде чем
  попасть в `/usr/local/bin/telemt`.
- Системную учётную запись `telemt`, чтобы служба работала без прав root.
- `tgwp-agent init-node --engine telemt`. Эта команда записывает `/etc/telemt/telemt.toml`,
  токен API управления в `/etc/telemt/api.token` (права 0600), unit
  `/etc/systemd/system/telemt.service` и сайт-прикрытие в `/var/lib/telemt/public`.
- Таблицу nftables `tgwp_telemt` (`/etc/nftables.d/tgwp-telemt.nft`, подключена из
  `/etc/nftables.conf`), которая закрывает внутренние порты снаружи.
- Агент: `/usr/local/bin/tgwp-agent`, его настройки в `/etc/tgwp-agent/agent.env` и unit
  `tgwp-agent.service`.

| Порт | Кому открыт | Кто его использует |
|---|---|---|
| 80 | Интернету | Caddy, выпуск сертификата |
| 443 | Интернету | Caddy: WEB-прокси и сайт-прикрытие |
| 8443 (порт Fake-TLS, `classic_port`) | Интернету | Fake-TLS |
| 9090 | Только loopback | Метрики telemt |
| 9091 | Только loopback | API управления telemt |
| 18080 | Только loopback | WEB-слушатель telemt за Caddy |

Порт Fake-TLS работает с правилами `synlimit` из telemt. Это защита от SYN-флуда, взятая из
MTPROTO_FIX_By_MEKO (см. [Благодарности](../README.ru.md#благодарности)).

telemt нужен публичный IPv4-адрес сервера. Скрипт установки берёт его из `TGWP_PUBLIC_IP`, если
переменная задана, затем из публичного IP, указанного для сервера в панели. Иначе он сравнивает
два адреса: адрес исходящего сетевого интерфейса и адрес, который видит `api.ipify.org`, и
выбирает тот, на который указывает A-запись сервера. Если не подошёл ни один, берётся адрес
интерфейса, когда он публичный. Если адрес найти не удалось, установка останавливается, ничего
не меняя: укажите публичный IP в панели и запустите команду снова. Исправить адрес можно и
позже, на вкладке «Настройки» сервера.

Сервер должен иметь доступ к собственному домену по порту 443. Fake-TLS-соединение с незнакомым
именем домена telemt передаёт домену Fake-TLS на порт 443, а этот домен обычно указывает на сам
сервер. Некоторые хостинги не дают серверу подключаться к собственному публичному адресу. Тогда
такие соединения обрываются, и любой, кто прощупывает сервер, вместо сайта-прикрытия видит
ошибку. Чтобы проверить, выполните `curl -sSI https://<домен сервера>/` на самом сервере: в
ответе должны прийти заголовки сайта-прикрытия.

### tproxy

Старая связка: `tproxy-server` из `https://github.com/telegramdesktop/tproxy-server` на коммите
`TPROXY_COMMIT`, официальный MTProxy, Caddy и агент. Первые три ставит скрипт `deploy/install.sh`
из репозитория tproxy-server. Сервер с tproxy занимает порты 80 и 443 и выдаёт каждому
пользователю только WEB-ссылку.

Каждое применение перезапускает `tproxy-server`, а если поменялись секреты MTProxy, то и MTProxy,
поэтому действующие сессии рвутся. Подробности есть в
[руководстве по эксплуатации](runbook.ru.md#на-сервере-с-tproxy). Чтобы перевести уже установленный сервер tproxy
на новый `TPROXY_COMMIT`, его нужно переустановить новой командой установки.

### Что перезапускает telemt

Большинство изменений доходит до telemt без перезапуска. В таблице перечислены те, что его
перезапускают. При перезапуске действующие соединения рвутся, клиенты Telegram переподключаются
сами.

| Изменение | Перезапуск telemt | Что будет со ссылками |
|---|---|---|
| Пользователи, их лимиты, сайт-прикрытие | Нет | У новых пользователей появятся ссылки, остальные не меняются |
| Домен или порт Fake-TLS | Да | Все выданные для этого сервера Fake-TLS-ссылки перестанут работать. WEB-ссылки продолжат работать |
| Запасные домены маскировки | Да | Выданные ссылки продолжат работать; каждый домен добавит пользователям по одной Fake-TLS-ссылке |
| Публичный IP | Да | Ничего, потому что в ссылках стоит имя домена |
| «Перезапустить telemt» на вкладке «Обслуживание» | Да | Ничего |
| Обновление telemt | Да, после завершения WEB-сессий | Ничего |

Первые три изменения делаются на вкладке «Настройки» страницы сервера, в карточке «Адреса и
Fake-TLS», и доходят до сервера со следующим применением. Домен и порт Fake-TLS входят в секрет
каждой Fake-TLS-ссылки, поэтому после смены любого из них разошлите людям новые ссылки.

Запасные домены маскировки выручают, когда провайдер начинает блокировать основной домен
Fake-TLS: человек берёт ссылку с другим доменом, а сервер переустанавливать не нужно. На сервер
можно добавить до восьми таких доменов, агент должен быть версии 2.9.2 или новее. Подходят
только настоящие сайты, которые отвечают по HTTPS на порту 443 и доступны с сервера: при запуске
telemt копирует TLS-отпечаток каждого домена, и если какой-то не отвечает, telemt не принимает
конфигурацию и применение откатывается.

### Настройка сети

Для обоих движков скрипт установки записывает `/etc/sysctl.d/90-tgwp.conf`, сетевые настройки для
прокси-сервера из MTPROTO_FIX_By_MEKO: BBR с планировщиком `fq`, увеличенные очереди приёма и SYN
(`somaxconn`, `tcp_max_syn_backlog`, `netdev_max_backlog` = 65535), TCP Fast Open и короткие
keepalive (45 и 15 секунд, 3 попытки), чтобы мёртвые клиенты отваливались примерно за минуту.
Скрипт применяет файл командой `sysctl --system`. Если ядро не принимает какой-то параметр,
например в контейнере или на старом ядре, скрипт сообщает об этом и продолжает работу. Файл можно
удалить, если серверу нужны свои значения.

### Обновление серверов

Какой telemt должен стоять на серверах, решает панель: пара `TELEMT_VERSION` и
`TELEMT_SHA256_X86_64` в её `.env`. Команда `sudo /opt/tgproxy-panel/install.sh --update`
переводит эту пару на значения из нового релиза панели. Серверы остаются на прежней версии, пока
вы их не обновите. Обновить можно тремя способами.

На самом сервере, по SSH под root:

```bash
tgwp-agent upgrade --check   # что изменится; ничего не меняет
tgwp-agent upgrade           # показывает план и спрашивает
tgwp-agent upgrade --yes     # без вопросов; обязательно, если нет терминала
```

Команда спрашивает у панели, что должно работать на сервере (`GET /api/v1/node/upgrade`, с
собственным токеном сервера из `/etc/tgwp-agent/agent.env`), и заменяет только то, что
отличается: бинарник telemt, бинарник агента или оба (`--telemt` и `--agent` сужают выбор).
Каждую загрузку она сверяет с sha256 из панели, сохраняет прежний бинарник, перезапускает службу
и ждёт, пока та не сообщит, что здорова. Если этого не происходит, прежний бинарник
возвращается. Токен установки не нужен.

В панели, для одного сервера: страница сервера → «Обслуживание» → блок «Версии» →
«Обновить telemt». Агент сверяет SHA256 загрузки, приостанавливает новые WEB-сессии, даёт
текущим до 120 секунд на завершение, заменяет бинарник, сохранив резервную копию, перезапускает
telemt, проверяет версию и готовность и снова открывает приём WEB-сессий. Итогом будет один
из `ok`, `refused`, `failed`, `rolled_back`, `rollback_failed` или `needs_attention`.
Обновление завершено только при `ok`.

В панели, для нескольких серверов: «Серверы» → «Обновить telemt…». Окно называет версию,
которую поставит, и перечисляет все серверы с telemt, у каждого — с какой версии на какую он
перейдёт. Поиск находит сервер по имени или адресу, «Выбрать устаревшие» отмечает все серверы на
связи со старой версией. Серверы обновляются по одному в порядке списка, поэтому первый служит
проверкой. После каждого обновления панель проверяет сервер и минуту наблюдает за
ним, прежде чем перейти к следующему. Ошибка останавливает очередь, а кнопка «Остановить
следующие обновления» даёт текущему обновлению завершиться.

При перезапуске telemt действующие сессии сервера рвутся, поэтому обновляйте серверы по одному.
Подробности и значения итогов описаны в [руководстве по эксплуатации](runbook.ru.md#обновление-telemt-не-удалось).

## Экраны панели

В боковом меню восемь разделов: «Обзор» и «Мониторинг» для наблюдения, «Серверы» и
«Сайты-прикрытия» для инфраструктуры, «Пользователи» в группе «Доступ», «Страница» в группе
«Подписка», а затем «Журнал действий» и «Настройки».

### Обзор

Главная страница показывает, всё ли работает и что требует вашего внимания. Блок «Требует
внимания» перечисляет открытые проблемы: какой сервер, что случилось и как давно, с действием,
которое это исправляет («Открыть», «Применить» или «Перезапустить»), и кнопкой «Прочитано».
Владелец и администратор могут отметить несколько проблем галочками и прочитать их вместе или
нажать «Прочитать всё»; прочитанная проблема уходит из списка, пока не решится и не случится
снова. Когда всё в порядке, блок так и пишет. Рядом четыре числа: люди онлайн с линией за 24
часа и числом соединений под ним, серверы на связи с именем того, который не отвечает,
активные пользователи из всех и трафик за 24 часа, а если у панели есть все предыдущие сутки, то
и разница с ними. Ниже идут карточки всех серверов в общем порядке и свёрнутый блок «График
людей онлайн и последние операции». Кнопка «Новый пользователь» открывает создание
пользователя.

Люди онлайн — примерное число, которое обновляется раз в минуту. Личный пользователь с хотя бы
одним соединением — один человек, общий — столько, сколько у него разных IP-адресов, а на
серверах с tproxy вместо людей считаются WEB-сессии. Одно приложение Telegram держит несколько
соединений, поэтому соединений всегда больше. Подробности есть в
[руководстве по мониторингу](monitoring.ru.md).

### Мониторинг

Страница «Мониторинг» собирает графики и историю. Её разделы:

| Раздел | Что показывает |
|---|---|
| Сводка | Серверы на связи, люди онлайн с числом соединений, самая большая задержка до Telegram, сертификат, который истекает раньше всех, текущий трафик, и карточка каждого сервера: люди онлайн, процессор, память, задержка до Telegram, сколько дней осталось сертификату, сколько сервер работает без перезагрузки, как давно ждут неприменённые изменения, доступное обновление telemt |
| По серверам | По каждому серверу: сессии и потоки, скорость отдачи и приёма, а также CPU, RAM и диск. У сервера с telemt вместо них линии людей онлайн и соединений и одна линия трафика |
| WEB-транспорт | WEB-транспорты по всем серверам с telemt |

Как собирать метрики панели в Prometheus, показано в «Настройки» → «Интеграции»; раньше здесь был
раздел «Экспорт метрик».

Период на вкладке «По серверам» выбирается из 1, 6 и 24 часов и 7 дней. Проблемы перечисляются
только на «Обзоре». Как собирать метрики панели в Prometheus, написано в «Настройки» →
«Интеграции»; старые ссылки на экспорт метрик открывают эту вкладку.

Графики строятся по снимкам: раз в минуту панель записывает состояние каждого сервера на связи
и хранит эти записи 30 дней.

Для Prometheus панель отдаёт `/metrics` в текстовом формате Prometheus. Нужен заголовок
`Authorization: Bearer <METRICS_TOKEN>`. Там есть `tgwp_nodes` и `tgwp_keys` (количество по
статусам), `tgwp_node_sessions_live`, `tgwp_node_streams_live` и `tgwp_node_people_online` (по UUID
сервера), `tgwp_people_online` и `tgwp_people_online_15m` (по всем серверам), а также
стандартные метрики `go_*` и `process_*`. Задание для сбора:

```yaml
scrape_configs:
  - job_name: tgwp-panel
    metrics_path: /metrics
    scheme: https
    scrape_interval: 60s
    authorization:
      credentials_file: /etc/prometheus/tgwp-token
    static_configs:
      - targets: ["panel.example.com"]
```

Готовый дашборд Grafana лежит в [`deploy/grafana/tgwp-panel.json`](../deploy/grafana/tgwp-panel.json),
пример настройки сбора в [`deploy/prometheus.example.yml`](../deploy/prometheus.example.yml).
В разделе [«Мониторинг»](monitoring.ru.md) описаны настройка, все метрики и то, какая статистика
по пользователям существует.

### Серверы

В списке для каждого сервера видны имя и домен, люди онлайн с числом соединений, CPU и RAM и
время последнего ответа. Нажатие в любом месте строки открывает сервер; применение изменений,
команда установки и удаление — на странице сервера. Серверы везде в панели идут в одном
порядке: так же их показывают «Обзор», «Мониторинг», выбор серверов у пользователя и страница
подписки. Владелец и администратор меняют порядок, перетаскивая строку за ручку, а с клавиатуры —
пробелом на ручке, стрелками и снова пробелом. Новый сервер встаёт в конец. Кнопка «Добавить
сервер» открывает мастер из трёх шагов:

1. «Сервер»: имя, домен, e-mail для сертификата Let's Encrypt и при необходимости публичный IP.
   Кнопка «Проверить DNS» показывает, куда домен указывает прямо сейчас.
2. «Прокси»: движок и, в блоке «Расширенные: маскировка и порты», домен Fake-TLS (по умолчанию
   домен сервера) и порт Fake-TLS (по умолчанию 8443; от 1024 до 65535, кроме 80 и 443).
3. «Установка»: одноразовая команда установки. Окно следит за агентом, пока тот не подключится.

Кнопка «Обновить telemt…» на той же странице обновляет несколько серверов подряд (см.
[Обновление серверов](#обновление-серверов)).

### Страница сервера

В шапке видны статус сервера, домен, версии движка и агента и кнопка «Применить изменения»: она
активна, пока у сервера есть неприменённые изменения. Вкладок пять:

| Вкладка | Что там |
|---|---|
| Состояние | Что не так, если что-то не так (у сервера не на связи ещё и команды для проверки). Строка главных цифр: статус, люди онлайн со ссылкой на пользователей этого сервера, процессор и память, задержка до Telegram, итог проверок. График людей онлайн, процессора и трафика за сутки или неделю. Разделы, которые раскрываются по нажатию: «Датацентры Telegram» (маршрут, задержка до каждого датацентра сейчас и во времени, маршруты до Telegram), «Службы» (состояние каждой службы, ресурсы сервера и их история, запас ресурсов, счётчики прокси), «Проверки сервера» («Полная проверка сервера» на telemt, «Проверка с панели», «Проверки из внешних сетей» и кнопка «Проверить сейчас») и на telemt «WEB-транспорт» (состояние, нагрузка, обучение транспортам за 24 часа и кнопки паузы, освобождения и возобновления WEB-сессий). Раздел с проблемой раскрыт сразу |
| Настройки | Только telemt: «Адреса и Fake-TLS» (публичный IP, домен и порт Fake-TLS, запасные домены маскировки, тег спонсорского канала) и свёрнутые «Стратегия транспорта» с защитой от перегрузки и «Надёжность и маршрут» |
| Сайт-прикрытие | Текущий шаблон, выбор другого и существующий HTTP-сайт на серверах с telemt, которые это поддерживают |
| Блокировки | Адреса и подсети, с которых сервер не принимает подключения |
| Обслуживание | Версии telemt и агента с обновлением telemt, действия (перезапуск telemt или relay, команда установки), история применений с логами, пользователи на сервере с кнопкой «Сверить с сервером» и отдельно удаление сервера |

Логов служб в панели нет: их смотрят на самом сервере, команды собраны в руководстве по
эксплуатации, в разделе [«Логи сервера»](runbook.ru.md#логи-сервера).

Раздел «Датацентры Telegram» показывает для каждого датацентра задержку, которую telemt измеряет
своими проверками, предпочтение IPv4 или IPv6 и состояние маршрута. Задержка до 150 мс зелёная,
до 400 мс жёлтая, а выше красная. У серверов с tproxy таких данных нет.

Тег спонсорского канала выдаёт бот @MTProxybot в Telegram. Когда тег задан, клиенты, подключённые
через этот сервер, видят спонсорский канал. Кнопки в карточке копируют адрес и секрет, которые
спросит бот. Ссылку, которую бот пришлёт после этого, раздавать не нужно: давайте
людям ссылки из раздела «Пользователи».

«Надёжность и маршрут» управляет двумя вещами. Восстановление определяет, что делает
агент, когда telemt перестаёт отвечать: только наблюдает или перезапускает его после нескольких
неудачных проверок подряд. Исходящий маршрут может направить трафик telemt к Telegram через
локальный SOCKS5, например WARP, с резервным маршрутом. Обе настройки описаны в руководстве
по эксплуатации, в разделе [«Автоматический перезапуск и маршрут до Telegram»](runbook.ru.md#автоматический-перезапуск-и-маршрут-до-telegram).

### Сайты-прикрытия

Галерея сайтов-прикрытий: 15 встроенных, ваши копии и импортированные сайты. Есть фильтр по
категориям, предпросмотр в размерах компьютера, планшета и телефона, кнопки «Настроить сайт»,
«Импорт ZIP» и «Свой сайт» для сайта, написанного с нуля в редакторе. Назначить сайт серверу можно
из галереи или со вкладки «Сайт-прикрытие» сервера. Как это устроено внутри:
[Как работают сайты-прикрытия](#как-работают-сайты-прикрытия).

### Пользователи

Над списком поиск по имени, контакту, заметке и короткому адресу и кнопки состояний с числами:
«Все», «Активные», «Скоро истекают» (в ближайшие 7 дней), «Срок истёк», «Выключены», а когда такие
есть, ещё «Настраиваются» и «Отозваны». «Фильтры» сужают список по типу и серверу, включённый фильтр
виден отдельной кнопкой с крестиком. Адрес `/users?node=<id>` открывает пользователей одного
сервера. Массовые действия: продлить, выключить, включить, отозвать доступ, удалить. Если под
фильтры никто не подошёл, есть кнопка «Сбросить фильтры». Кнопка «Колонки» прячет и показывает
столбцы (активность, срок, трафик за 30 дней, серверы, тип, ссылка с кнопкой копирования, дата
создания), выбор запоминается в браузере. Под списком написано, какие строки показаны, и можно
выбрать 25, 50 или 100 строк на странице; выбор запоминается, а номер страницы виден в адресе.
Меню «⋯» в строке: «Скопировать ссылку», «Продлить на месяц», «Выключить» или «Включить»,
«Удалить». Нажатие на любое место строки открывает окно пользователя с вкладками «Главное»,
«Доступ и серверы», «Лимиты» и «Статистика». Раньше раздел назывался «Ключи доступа», адреса
`/keys` и `/keys?key=<id>` ведут на `/users` и `/users?user=<id>`. Всё о пользователях собрано в
разделе [Пользователи и ссылки](#пользователи-и-ссылки).

### Подписка

В группе «Подписка» два раздела. «Страница» настраивает публичную страницу подписки: язык,
первую вкладку, заголовок и приветствие, какие ссылки и серверы показывать. Там же живой
предпросмотр, он всегда работает на панели. Раньше эти настройки были вкладкой в «Настройках».
«Сервис» решает, где открываются страницы: на домене панели или на своём домене, на сервере
панели или на отдельном сервере. Его видят владелец и администратор, менять может только
владелец. Подробности в разделах [Страница подписки](#страница-подписки) и
[Страницы подписки на своём домене](#страницы-подписки-на-своём-домене).

### Журнал действий

Все изменения, сделанные в панели, и все входы, включая неудачные: кто, когда, с какого IP и что
изменилось. Фильтры: действие, пользователь и даты. Фильтр по действию ищет по началу названия,
поэтому `key.` находит `key.create`, `key.revoke` и остальные. Сброс 2FA из командной строки
попадает сюда как `auth.totp_reset`.

### Настройки

Вкладки делятся на две группы: вкладки «Для всей панели» действуют на всех, а «Только для вас»
касаются только вашей учётной записи.

| Вкладка | Группа | Что там | Кто может менять |
|---|---|---|---|
| Уведомления | Для всей панели | Как часто применять изменения (от 10 до 3600 с), когда считать сервер недоступным (от 30 до 3600 с), уведомления в Telegram | Владелец |
| Интеграции | Для всей панели | Экспорт метрик в Prometheus и Grafana с примером настройки, задан ли `METRICS_TOKEN`, настроен ли вебхук оповещений и как его включить | Только просмотр: оба задаются в `.env` |
| Оформление | Для всей панели | Варианты оформления: название панели, логотип, логотип для тёмной темы, favicon, фон страницы входа, цвета, тема по умолчанию, тексты, свой CSS | Владелец и администратор |
| Учётные записи | Для всей панели | Учётные записи панели и их роли | Владелец |
| Резервные копии | Для всей панели | Резервные копии базы и ежедневное расписание | Владелец |
| Мой интерфейс | Только для вас | Тема (светлая, тёмная, как в системе), плотность, свёрнутое или развёрнутое меню. Хранится в этом браузере | Все |
| Пароль и 2FA | Только для вас | Смена пароля, двухфакторный вход | Все |

Изменения оформления применяются сразу, без пересборки. Активный вариант оформляет страницу
входа, интерфейс и все публичные страницы подписки. Изображения загружаются сразу (PNG, JPEG, ICO
или SVG, до 2 МБ), название, цвета и тексты сохраняются кнопкой «Сохранить». Стандартные цвета:
бирюзовый `#3fc0d6` и зелёно-бирюзовый `#20c997`, под светлую тему они подстраиваются сами.

### Верхняя строка, поиск и подсказки

В верхней строке видны версия панели, проект на GitHub с числом звёзд и число серверов онлайн.
Раз в час панель узнаёт на GitHub номер последнего релиза. Если вышла новая версия, значок версии
подсвечивается и ведёт на страницу релиза. О вашей установке панель ничего не отправляет, а
`UPDATE_CHECK=false` отключает проверку.

`⌘K` или `Ctrl+K` открывает командную палитру: переход к разделу, поиск сервера или
пользователя, создание пользователя, применение изменений на всех серверах, смена темы или
языка.

Кнопка `?` в заголовке каждой страницы и каждого окна открывает справку по этому экрану: что
значит каждое поле, пример значения, что будет, если оставить поле пустым. Клавиша `?` делает то
же самое.

Формы запоминают введённое. Если окно случайно закрылось, при следующем открытии панель предложит
восстановить черновик. Черновик хранится в браузере 24 часа, пароли и токены в него не
сохраняются.

## Пользователи и ссылки

Пользователь даёт доступ к прокси одному человеку или группе людей. В API и в базе он
по-прежнему называется ключом: адреса `/api/v1/keys`, таблица `access_keys`, действия `key.*` в
журнале. В окне «Новый пользователь» три вкладки:

| Вкладка | Что создаёт |
|---|---|
| Один человек | Личного пользователя (`PERSONAL`). Его можно выключить или отозвать, не трогая остальных |
| Общий доступ | Одного пользователя (`SHARED`) на группу людей с общей ссылкой. Выключается и отзывается он только для всех сразу, и только у него бывает короткий адрес |
| Несколько | До 100 личных пользователей за раз с именами `prefix-1`, `prefix-2` и так далее. Окно в этом режиме называется «Несколько пользователей», префикс и количество задаются в карточке «Имена». Панель проверяет, что на каждом сервере хватит мест, и создаёт либо всех, либо никого. В результате у каждого есть кнопка копирования ссылки подписки, а «Скачать все ссылки (.txt)» сохраняет файл: сначала ссылки подписки, потом прямые ссылки по серверам |

Поля: «Имя», чтобы потом найти пользователя в списке (обязательно); «Контакт», например ник в
Telegram, телефон или почта (необязательно); «Короткий адрес» у общего доступа; «Заметка»;
«Срок доступа» с кнопками «+1 месяц», «+3 месяца», «+1 год» или «Без срока»; серверы; лимиты.
Пользователя можно поставить на несколько серверов, тогда человек получит ссылки для каждого из
них. По умолчанию на сервер помещается до 128 пользователей. Каждый новый пользователь сразу
получает ссылку подписки.

Состояние пользователя видно в списке и в его окне:

| Состояние | Что значит |
|---|---|
| Настраивается (`pending`) | Панель настраивает серверы, обычно это меньше минуты. Ничего нажимать не нужно |
| Активен (`active`) | Доступ работает |
| Выключен (`disabled`) | Доступ на паузе: пользователь снят с серверов, ссылки и настройки сохранены. Переключатель «Доступ включён» в окне пользователя или «Включить» возвращает доступ |
| Срок истёк (`expired`) | Дата прошла, и пользователь снят с серверов. Если продлить срок и сохранить, доступ вернётся с прежними ссылками |
| Отозван (`revoked`) | Доступ закрыт насовсем. Пользователь остаётся в списке для истории, его настройки только для чтения |

Выключенного пользователя и пользователя с истёкшим сроком сервер с telemt держит у себя
отключённым, а сервер с tproxy убирает его секрет. Пользователи, которых прошлые версии панели
отозвали по сроку, остаются отозванными.

«Сменить секрет» даёт пользователю новый секрет: прямые ссылки меняются, старые перестают
работать, а ссылка подписки остаётся прежней. «Отозвать доступ» закрывает доступ насовсем,
«Удалить» убирает пользователя вместе с его ссылками и статистикой.

### Ссылки

Каждый сервер даёт пользователю свои прямые ссылки. Они открываются строкой «Прямые ссылки на
прокси» в окне пользователя, у каждой есть QR-код и кнопки копирования в формате `t.me` и `tg://`.

| Ссылка | Формат | Где работает |
|---|---|---|
| WEB | `https://t.me/webproxy?server=<домен>&secret=<секрет>` | Telegram Desktop; Android экспериментально, iOS в планах |
| Fake-TLS | `https://t.me/proxy?server=<домен>&port=<порт Fake-TLS>&secret=ee…` | Все приложения Telegram |

Сервер с tproxy даёт только WEB-ссылку. Сервер с telemt даёт обе и ещё по одной Fake-TLS-ссылке
на каждый запасной домен маскировки.

### Лимиты

На серверах с telemt у пользователя можно задать квоту трафика в ГБ, скорость отдачи и приёма
в Мбит/с, максимум уникальных IP-адресов и максимум соединений. Их соблюдает сам telemt. Пустое
поле означает «без ограничения». Расширенные лимиты (сессии, потоки и подобные) в основном
относятся к серверам с tproxy, из них telemt берёт только лимиты сессий и потоков. На серверах с
tproxy у пользователя есть ещё режим передачи: HTTPS (по умолчанию), HTTPS lanes, WebSocket или
WebSocket lanes. На telemt WEB-транспорт подбирается для каждого подключения автоматически.

Квоту можно сбрасывать по расписанию: поле «Сброс квоты» — «Никогда», «Каждую неделю» или
«Каждый месяц». Неделя начинается в понедельник, месяц — первого числа, оба в 00:00 UTC. В
начале периода панель отправляет серверам новое задание, и агент один раз обнуляет израсходованный
трафик пользователя; сама квота не меняется. Если панель или сервер были недоступны в момент
смены периода, сброс случится при первом применении после этого. Включение расписания посреди
периода квоту не обнуляет: первый сброс будет в начале следующего периода.

На серверах с telemt панель также считает трафик по пользователям. В окне пользователя видны
трафик за 30 дней и то, в сети ли человек, примерно со скольких устройств (разных IP-адресов на
всех серверах) и через сколько соединений, или когда он подключался последний раз. Вкладка
«Статистика» показывает график за 24 часа или 7 дней.

### Страница подписки

У каждого пользователя есть публичная ссылка подписки, панель создаёт её вместе с пользователем.
Ссылка открывает страницу, которая ведёт человека по подключению: вкладки для Android, iPhone и
iPad и компьютера, и на каждой три шага (установить Telegram, нажать «Подключить» рядом с сервером,
подтвердить в Telegram). Кнопка «Подключить» берёт ссылку, которую устройство умеет открыть: на
iPhone Fake-TLS, на Android Fake-TLS с WEB-прокси запасным вариантом, на компьютере WEB-прокси с
запасным Fake-TLS. На iPhone вторым вариантом служит Fake-TLS-ссылка на запасной домен маскировки,
если он есть у сервера. Ниже, в блоке «Все ссылки и QR-коды», перечислены все ссылки. Доменов
серверов в карточках на странице нет. Если вкладку «Компьютер» открыли на телефоне, страница
предлагает отправить ссылку на себя и открыть её на компьютере, с кнопкой «Скопировать ссылку на
страницу». Если вкладку телефона открыли на компьютере и QR-коды включены, страница показывает
QR-код самой себя, чтобы открыть её на телефоне. Страница показывает, до какого числа действует
доступ, а имя пользователя, контакт и заметка на ней никогда не показываются. Переключатель RU/EN
вверху меняет язык, а выбранные язык и вкладку страница запоминает в этом браузере.

Что показывать на странице, решается в разделе «Подписка» → «Страница», там же живой
предпросмотр. Старый адрес `/settings?section=subscription` ведёт туда же.

| Настройка | Что делает |
|---|---|
| Язык страницы | По языку браузера посетителя (по умолчанию), русский или английский |
| Какую вкладку открыть первой | По устройству посетителя (по умолчанию) или всегда Android, iPhone и iPad, Компьютер |
| Заголовок и приветствие | Текст в шапке, отдельно на русском и на английском; пустые поля заменяются на «Подключение к Telegram» и стандартное приветствие на языке страницы |
| Какие ссылки показывать | Fake-TLS, WEB-прокси, запасные домены; хотя бы одно из первых двух остаётся включённым |
| Что ещё показать | Инструкция по шагам, срок действия доступа, QR-коды |
| Серверы на странице | Сервер без галочки не попадает ни на одну страницу подписки, пользователи на нём продолжают работать |

Те же фильтры действуют и для JSON.

- Панель хранит ссылку подписки в двух видах: хеш SHA-256, по которому она находит пользователя,
  когда страницу открывают, и копию, зашифрованную `MASTER_KEY`. Поэтому ссылку можно
  скопировать или показать QR-кодом в любой момент.
- Ссылки, выпущенные в прошлых версиях панели, хранятся только как хеш. Они работают, но
  показать их нельзя. Кнопка «Выпустить новую ссылку» в окне пользователя после подтверждения
  заменяет такую ссылку новой, и старая перестаёт открываться.
- «Новая ссылка подписки» в меню «Ещё действия» заменяет ссылку, старая сразу перестаёт
  открываться. Прокси, уже добавленные в Telegram, продолжают работать.
- «Отозвать ссылку» отключает её, после этого на её месте появляется «Создать ссылку».
- «Сменить секрет» ссылку подписки не меняет: чтобы получить новые прямые ссылки, человеку
  достаточно открыть её и снова нажать «Подключить».

У общего доступа может быть короткий адрес `/s/<slug>`: от 3 до 32 символов, строчные латинские
буквы, цифры и дефис, дефис не в начале и не в конце. При вводе панель переводит кириллицу в
латиницу, а пробелы в дефисы. Адрес должен быть свободен. Он открывает
ту же страницу, что и длинная ссылка, пока у пользователя есть действующая ссылка подписки.

Страница открывается по адресу `/s/<token>` или `/s/<slug>`, а с окончанием `.json` отдаёт те
же данные в JSON. Эти адреса публичные, не больше 60 запросов в минуту с одного IP-адреса, и
никогда не кешируются. Если доступа по ссылке нет, страница объясняет почему, а JSON отвечает
тем же кодом:

| Случай | Код | Что пишет страница |
|---|---|---|
| Неизвестная или отозванная ссылка подписки | 404 | «Ссылка не найдена.» |
| Доступ отозван | 410 | «Эта ссылка больше не действительна.» |
| Доступ выключен | 403 | «Доступ по этой ссылке временно выключен. Напишите тому, кто прислал вам ссылку.» |
| Срок истёк | 410 | «Срок доступа по этой ссылке закончился. Напишите тому, кто прислал вам ссылку, чтобы его продлили.» |

### Страницы подписки на своём домене

По умолчанию ссылки подписки строятся на домене панели (`PANEL_PUBLIC_URL`). В «Подписка» →
«Сервис» можно выбрать «На своём домене» и указать другой домен, только сам домен без пути,
например `sub.example.com`. Он должен отличаться от домена панели, иначе панель ответит 422.
После сохранения все ссылки подписки, короткие адреса и QR-коды в панели строятся на этом
домене. Старые ссылки `/s/…` на домене панели отвечают перенаправлением 302 на тот же путь на
новом домене. Галочка «Не открывать страницы на домене панели» заменяет перенаправление страницей
«Ссылка не найдена» с кодом 404: домен панели нигде не виден, но старые ссылки перестают работать.
«Проверить домен» открывает `https://<домен>/healthz`.

Обслуживать домен можно двумя способами:

| Способ | Как устроен |
|---|---|
| На сервере панели | `install.sh --update --sub-domain sub.example.com` пишет `sites/subpage.caddy` в каталог панели, Caddy панели подключает его и получает сертификат. С этого момента панель отдаёт на нём только `/s/*`, `/healthz` и `robots.txt`, на остальное отвечает 404 (домен она узнаёт из `SUBPAGE_DOMAIN` в `.env`). `--sub-domain off` убирает файл |
| На другом сервере | `install.sh --subpage` ставит в `/opt/tgproxy-subpage` два контейнера: `subpage` (тот же образ, что у панели, с командой `subpage`) и Caddy с сертификатом на домен. Команду с токеном выдаёт кнопка «Получить команду установки» |

Сервис на другом сервере не хранит базу. На каждую ссылку он спрашивает панель
(`GET /api/v1/subpage/pages/{token}` с заголовком `Authorization: Bearer <токен сервиса>`),
держит ответ 30 секунд, а если панель недоступна, до 6 часов показывает сохранённую копию. Если
копии нет, он отвечает 503 и просит повторить через минуту. С одного IP-адреса он принимает не
больше 60 запросов в минуту. `/healthz` отвечает `{"ok":true,"panel_reachable":…,"version":…}`,
где `panel_reachable` говорит, отвечала ли панель в последние три минуты. Раз в минуту сервис
отправляет панели `POST /api/v1/subpage/heartbeat` со своей версией. «Сервис» в панели показывает
«на связи», если такой сигнал пришёл не больше трёх минут назад, время последнего сигнала, версию
сервиса (с предупреждением, если она не совпадает с версией панели) и адрес, с которого пришёл
сигнал. Токен сервиса панель хранит только как хеш, а показывает один раз, внутри команды
установки. «Новый токен» после подтверждения делает старый недействительным. «Отключить сервис»
отзывает токен: панель начинает отвечать сервису 401, и он какое-то время живёт на сохранённых
копиях.

## Как работают сайты-прикрытия

Каждый, кто откроет домен прокси-сервера в браузере, увидит обычный сайт. Это и есть
сайт-прикрытие. На сервере с telemt его показывает сам telemt, на сервере с tproxy его
показывает relay.

В панели 15 встроенных сайтов: `acorn`, `atlasdocs`, `cloudmetrics`, `corporate`, `dailybrief`,
`frame`, `kansocoffee`, `lumanotes`, `maison`, `nomad`, `northstar`, `orbitcdn`, `personal`,
`pixelforge` и `status`. Кроме них можно:

- настроить встроенный сайт: получится редактируемая копия с вашим названием компании,
  заголовком, описанием, контактной почтой и текстом внизу страницы;
- импортировать статический сайт архивом ZIP с `index.html` в корне (одна вложенная папка тоже
  подойдёт). В нём могут быть HTML, CSS, JavaScript и локальные файлы, до 512 файлов и до 2 МБ
  после распаковки. Пути и типы файлов проверяются, а на панели из архива ничего не запускается;
- написать сайт в редакторе. Он не пропускает внешние ресурсы, формы и встроенные обработчики
  событий и выносит встроенные стили и скрипты в отдельные файлы.

Прежде чем сайт попадёт на сервер, панель делает для этого сервера его уникальную копию:
перемешивает порядок блоков страницы, переименовывает CSS-классы и файлы и выбирает между
вариантами формулировок, если они есть в шаблоне. Копия зависит от ID сервера, поэтому два сервера
с одним шаблоном отдают разный HTML, а один и тот же сервер всегда получает одинаковый результат.
Повторное назначение того же шаблона ничего не меняет и ничего не перезапускает. Так посторонний
не сможет найти все ваши серверы, сравнивая их страницы.

Сервер с telemt, который сообщает о такой возможности, может показывать вместо шаблона уже
существующий HTTP-сайт: кнопка «HTTP-сайт» на вкладке «Сайт-прикрытие». Принимаются только адреса
`http://` с loopback или частным IP. Перед переключением агент проверяет адрес на самом сервере.

После смены сайта откройте домен сервера в браузере и проверьте, что на месте картинки и стили.
Предпросмотр в редакторе не показывает, что на самом деле развёрнуто.

## Проверки, инциденты и оповещения

### Проверка с панели

Кнопка «Проверить сейчас» у раздела «Проверки сервера» на вкладке «Состояние» заставляет
панель проверить сервер снаружи, а на серверах с telemt запускает и полную проверку. Результат сохраняется вместе с сервером. Проверки идут по
порядку, и на все вместе отведено 15 секунд:

| Проверка | Что проверяет |
|---|---|
| `dns_a` | Домен находится в DNS, и один из его адресов совпадает с IP сервера, если панель его знает |
| `tcp_80` | Порт 80 отвечает. Он нужен для сертификата и перенаправления с HTTP |
| `tcp_443` | Порт 443 отвечает. Если нет, следующие три проверки пропускаются |
| `tls_cert` | Сертификат подходит к домену и не истекает в ближайшие 7 дней |
| `pq_kex` | TLS-фронт договаривается о постквантовом обмене ключами `X25519MLKEM768`. Проверка информационная и не влияет на общий результат |
| `http_root` | `https://<домен>/` отвечает кодом 200 и непустой страницей. Перенаправления не выполняются |
| `mask` | Только telemt: порт Fake-TLS на запрос с доменом Fake-TLS и без ключа отвечает сертификатом, который подходит к этому домену |

Что делать, если проверка не прошла, описано в [руководстве по эксплуатации](runbook.ru.md#проверка-нашла-ошибку).

### Полная проверка сервера

На серверах с telemt «Полная проверка сервера» смотрит на сервер с двух сторон: снаружи, как
описано выше, и изнутри, через агента. Проверки разбиты на группы: DNS, порты и TLS, Caddy,
WEB-транспорт, telemt, Telegram и доступность каждого публичного IP-адреса. Каждая проверка
проходит, даёт замечание, не проходит или не выполняется. Невыполненные проверки считаются
отдельно и никогда не засчитываются как пройденные. Результаты хранятся в истории, кнопка
«Скачать отчёт» сохраняет результат в JSON.

Панель запускает эту проверку и сама, не чаще раза в 15 минут для каждого сервера на связи.

### Внешние проверки

Проверка из сети панели не показывает, как сервер выглядит из других сетей. Для этого есть
`tgwp-probe`, небольшая программа, которую запускают по таймеру в других сетях. Она делает
настоящее TLS-рукопожатие с сервером и открывает сайт-прикрытие. С закрытым файлом тестовых
секретов она также выполняет авторизованный обмен с Telegram через Fake-TLS и WEB; собственный
клиентский адаптер тоже поддерживается. Результаты видны в блоке
«Проверки из внешних сетей» раздела «Проверки сервера». Отчёт старше трёх минут считается
отсутствующим и открывает инцидент.

Включаются внешние проверки переменными `PROBE_TOKEN` и `PROBE_LOCATIONS` в `.env` панели.
Службу и таймер systemd можно взять в `deploy/probe`, а настройка описана в
руководстве по эксплуатации, в разделе [«Проверки из других сетей»](runbook.ru.md#проверки-из-других-сетей).

### Инциденты

Инцидент — это проблема, которую панель нашла сама. Он появляется в блоке «Требует внимания» на
«Обзоре». Большинство инцидентов закрываются сами, когда проблема уходит. «Прочитано» убирает
инцидент из списка, не закрывая его: пока проблема держится, он скрыт, и проверка, которая его
нашла, не поднимает его заново, поэтому он появится снова, только когда проблема уйдёт и
вернётся. Применение, которое падает и повторяется, остаётся одним инцидентом, пока очередное
применение не пройдёт. Инциденты открываются по таким причинам:

- сервер перестал выходить на связь, применение не удалось;
- отчёты агента: диск заполнен на 90% и больше, память на 95% и больше, движок не готов, приём
  WEB-сессий закрыт, заканчиваются файловые дескрипторы или таблица соединений, слишком много
  неудачных подключений к Telegram, недоступен исходящий маршрут;
- плановые полные проверки сервера;
- внешние проверки, которые не прошли или перестали присылать отчёты;
- резервную копию не удалось зашифровать или выгрузить.

### Оповещения в Telegram и вебхук

«Настройки» → «Уведомления»: введите токен бота и Chat ID, отметьте «Включить уведомления» и
сохраните. Кнопка «Отправить тестовое сообщение» работает и до сохранения: она берёт то, что
введено в форме, а для пустых полей сохранённые значения. Токен хранится зашифрованным и никогда не
возвращается в браузер.

Состояние серверов приходит короткими сводками. Проблемы датацентров, маршрутов, ресурсов и
проверок объединяются в одно уведомление на сервер. Подробности остаются в панели. Язык задаётся
полем «Язык уведомлений», по умолчанию русский; вебхук получает тот же текст без оформления.

- О потере связи с агентом панель сообщает после дополнительной задержки 3 минуты; это отдельное
  событие и не означает, что сам прокси остановлен.
- Сводка о проблемах приходит после 5 минут устойчиво плохого состояния. Смена проблемного
  датацентра не создаёт новое сообщение. Пока эпизод продолжается, повторных сводок нет.
- Восстановление приходит после 10 минут стабильных успешных проверок и только в те каналы,
  куда удалось доставить предупреждение. Новая ошибка сбрасывает ожидание восстановления.
- Устаревшие или отсутствующие измерения не считаются восстановлением. После перерыва наблюдений
  отсчёт устойчивого состояния начинается заново.
- Состояние уведомлений хранится в базе и переживает перезапуск панели. Ошибка доставки не
  считается успешной отправкой; Telegram и вебхук повторяются независимо.
- Неудачные применения сохраняют отдельное ограничение: не чаще одного сообщения в час.

Детальные инциденты в панели по-прежнему открываются после 3 неудачных минутных проверок и
закрываются после 3 удачных; это отдельный механизм от задержек Telegram. Плановым проверкам
нужны 2 неудачных прогона. Отсутствие Middle Proxy-соединений с датацентром означает ухудшение
этого маршрута, но не доказывает полный отказ Telegram: может работать прямой резервный маршрут.

Если сообщения не приходят, загляните в [руководство по эксплуатации](runbook.ru.md#не-приходят-уведомления-в-telegram).

Те же сообщения можно получать на свой HTTPS-адрес: задайте `ALERT_WEBHOOK_URL` и
`ALERT_WEBHOOK_SECRET`. Вебхук работает независимо от того, включён ли бот в Telegram. Панель
отправляет JSON с полями `event_id`, `node_id`, `kind`, `message` и `at`, делает до трёх попыток и
не следует перенаправлениям. Каждый запрос подписан HMAC-SHA256 в заголовке `X-TGWP-Signature`,
подпись считается от значения `X-TGWP-Timestamp`, точки и тела запроса.
В «Настройки» → «Интеграции» видно, настроен ли вебхук; сам адрес и секрет панель никуда не
отдаёт.

## Учётные записи и безопасность

### Роли

| Роль | Что может |
|---|---|
| `owner` | Всё, включая настройки панели, тестовое сообщение в Telegram, учётные записи и резервные копии |
| `admin` | Всё остальное: серверы, пользователи, сайты-прикрытия, применения, проверки, обновления, закрытие проблем, оформление |
| `viewer` | Только смотреть. Ссылки подписки, прямые ссылки и секреты пользователей ему не видны, API не отдаёт их этой роли, менять он может свой пароль и второй фактор, а также управлять своими персональными API-токенами только для чтения |

Первую учётную запись с ролью `owner` создаёт установщик. Остальные добавляются в «Настройки» →
«Учётные записи», пароль должен быть не короче 10 символов.

### Двухфакторный вход

Двухфакторный вход доступен по умолчанию, `FEATURE_TOTP=false` в `.env` его прячет. В
«Настройки» → «Пароль и 2FA» есть кнопка «Включить»:

1. Панель показывает QR-код и ключ для ручного ввода. Подойдёт любое обычное
   приложение-аутентификатор: Google Authenticator, Aegis, 1Password и другие.
2. Введите код из приложения и свой текущий пароль. Пароль не даёт тому, кто перехватил ваш
   сеанс, привязать своё приложение. После включения все остальные ваши сеансы завершаются.
3. Панель один раз показывает восемь резервных кодов вида `xxxxx-xxxxx`. Каждый срабатывает один
   раз. Сохраните их до того, как закроете окно.

С этого момента после пароля панель спрашивает код. На второй шаг даётся пять минут. Чтобы
выключить 2FA, нужны пароль и код из приложения или резервный код.

Если человек потерял и приложение, и резервные коды, владелец сбрасывает ему второй фактор на
сервере панели:

```bash
docker compose exec panel /app/panel admin totp-reset <username>
```

Подробности в руководстве по эксплуатации: [Потеря второго фактора](runbook.ru.md#потеря-второго-фактора).

### Как хранятся секреты

- Секреты пользователей и профилей, ссылки подписки, секреты TOTP и токен бота Telegram хранятся
  в базе зашифрованными с помощью `MASTER_KEY` (AES-256-GCM). Без этого ключа их не расшифровать,
  даже из резервной копии.
- Персональные API-токены, токены агентов, токены установки и токен сервиса страниц подписки
  хранятся только в виде хешей SHA-256. Сам токен
  показывается один раз, так что копия базы не даёт ни одного рабочего токена. У ссылки подписки
  рядом с зашифрованной копией лежит её хеш: по нему панель находит пользователя, когда страницу
  открывают.
- Сессионные cookie подписаны `SESSION_SECRET` и помечены `HttpOnly`. Изменения через браузерный
  сеанс требуют `X-CSRF-Token`, совпадающий с CSRF-cookie. Проверенные персональные Bearer-токены
  не требуют CSRF; смена пароля отзывает все персональные токены.
- `/metrics` показывает UUID серверов и количество серверов и пользователей. Его защищает
  `METRICS_TOKEN`, обязательный при `NODE_DRIVER=gateway`. Давайте этот токен только своему
  Prometheus.
- Загруженные SVG проверяются и отклоняются, если в них есть скрипты. Файлы оформления отдаются с
  заголовками `Content-Security-Policy: default-src 'none'; style-src 'unsafe-inline'; sandbox` и
  `X-Content-Type-Options: nosniff`.
- Сама по себе панель обращается только к GitHub, чтобы проверить обновления. Telegram, вебхук и
  выгрузка резервных копий используются, только если вы их настроили.
- Никогда не добавляйте `.env`, `MASTER_KEY` и `SESSION_SECRET` в репозиторий.

## Резервные копии и мастер-ключ

### Резервные копии

«Настройки» → «Резервные копии» (только владелец). «Создать копию» делает дамп всей базы через
`pg_dump`. «Ежедневная копия» делает копию раз в сутки в выбранный час (UTC) и хранит выбранное
число копий, от 1 до 60; более старые удаляются. Копии, созданные вручную, автоматически не
удаляются. Файлы лежат в `DATA_DIR/backups`, в установке через Docker это `/data/backups` на томе
`paneldata`. Любой файл можно скачать из таблицы. Одновременно создаётся только одна копия.

Сделать копию можно и на сервере панели: `docker compose exec panel /app/panel db backup`. В `.env` можно
включить дополнительную защиту: шифровать каждую копию через age (`BACKUP_AGE_RECIPIENT`),
выгружать её в ваше хранилище (`BACKUP_UPLOAD_URL`) и проверять, что она восстанавливается
(`BACKUP_VERIFY`). См. [Переменные окружения](#переменные-окружения).

Восстановление заменяет всю базу, поэтому оно делается из командной строки при остановленной
панели: [Резервные копии и восстановление](runbook.ru.md#резервные-копии-и-восстановление).

### Мастер-ключ

`MASTER_KEY` в `.env` шифрует секреты в базе. В резервной копии есть база, но нет этого ключа.
Храните копию `.env` не на сервере панели: без `MASTER_KEY` и старых значений `MASTER_KEY_V<n>`,
если они есть, восстановленная база не расшифрует ни одного секрета.

Ключ можно сменить. Команда `panel keys rotate` перешифровывает все секреты, включая ссылки
подписки, новым ключом в одной транзакции, при остановленной панели:

```bash
docker compose stop panel
docker compose run --rm panel keys rotate --dry-run   # считает строки, ничего не пишет
docker compose run --rm panel keys rotate             # перешифровывает и печатает строки для .env
docker compose up -d panel                            # после правки .env; start оставил бы старый ключ
```

Новый ключ команда берёт из `MASTER_KEY_NEW` и отказывается работать, если он совпадает с
текущим. Сами ключи она никогда не печатает. Полная процедура:
[Смена мастер-ключа](runbook.ru.md#смена-мастер-ключа).

## Подробности установки

Установка по шагам описана в гиде [«С нуля»](start.ru.md) и в
[инструкции по установке](setup.ru.md). Здесь собраны подробности.

### Установщик панели

```bash
curl -fsSL https://raw.githubusercontent.com/greenpandorik/tgproxy-panel/main/install.sh | sudo bash
```

Скрипт спрашивает домен, e-mail для сертификата и данные администратора или берёт их из
параметров. Он ставит Docker, если его нет, кладёт файлы в `/opt/tgproxy-panel`, создаёт `.env` с
новыми секретами, запускает сервисы и создаёт первого администратора. В конце он печатает адрес
панели и, если вы не задали пароль, сгенерированный пароль, один раз. В каталоге лежат
`docker-compose.yml`, `Caddyfile`, `.env` (права 0600) и копия скрипта.

```bash
sudo /opt/tgproxy-panel/install.sh --update              # перейти на последний релиз (или --version 1.2.0)
sudo /opt/tgproxy-panel/install.sh --uninstall           # остановить; спросит, удалять ли тома с данными
sudo /opt/tgproxy-panel/install.sh --uninstall --purge   # удалить контейнеры, тома и каталог
cd /opt/tgproxy-panel && docker compose logs -f panel    # логи
```

Прежде чем что-то менять, скрипт проверяет, что домен указывает на этот сервер, что порты 80 и
443 свободны (в локальном режиме 8080) и что каталогом установки можно пользоваться. Если
проверка не прошла и есть терминал, скрипт предлагает повторить, продолжить или выйти; без
терминала он останавливается. Файрвол скрипт не трогает, порты открывайте сами. Полный список
параметров есть в разделе [Командная строка](#installsh). Опубликованный образ собран для
`linux/amd64` и `linux/arm64`.

К каждому релизу также приложены бинарники `panel-linux-{amd64,arm64}` и
`tgwp-agent-linux-{amd64,arm64}` с файлом `SHA256SUMS`.

### Ручная установка через Docker Compose

На сервере панели нужен Docker с Compose v2 (`docker compose ...`).

```bash
cd deploy
cp ../.env.example .env
# заполните MASTER_KEY и SESSION_SECRET (по 32 случайных байта в base64):
sed -i.bak "s|^MASTER_KEY=.*|MASTER_KEY=$(openssl rand -base64 32)|" .env
sed -i.bak "s|^SESSION_SECRET=.*|SESSION_SECRET=$(openssl rand -base64 32)|" .env
sed -i.bak "s|^METRICS_TOKEN=.*|METRICS_TOKEN=$(openssl rand -hex 32)|" .env && rm .env.bak

# за Caddy, на настоящем домене, с TLS:
docker compose up -d --build postgres panel caddy

# или локально, без Caddy и TLS, панель прямо на :8080:
docker compose -f docker-compose.yml -f docker-compose.override.example.yml up -d --build postgres panel
```

Для настоящего домена задайте в `.env` `PANEL_DOMAIN=panel.example.com` и
`PANEL_PUBLIC_URL=https://panel.example.com`. При `PANEL_DOMAIN=localhost` (значение по
умолчанию) Caddy выпускает собственный самоподписанный сертификат. Либо добавьте его локальный
центр сертификации в доверенные (`docker compose exec caddy caddy trust`), либо используйте
`curl --insecure`.

Чтобы запустить готовый опубликованный образ без сборки из исходников, используйте
`deploy/docker-compose.release.yml`, тот же файл, что ставит установщик. В нём образ панели
`ghcr.io/greenpandorik/tgproxy-panel:${PANEL_VERSION:-latest}`, Caddy запускается в профиле
`caddy`, а `deploy/docker-compose.local.yml` открывает порт 8080 для локального режима. Данные
лежат в томах `pgdata`, `paneldata` и `caddydata`.

### Первый администратор

Установщик создаёт первого администратора сам. После ручной установки создайте его в запущенном
контейнере панели:

```bash
docker compose exec panel /app/panel admin create <username> <password>
```

Четвёртый аргумент задаёт роль: `owner` (по умолчанию), `admin` или `viewer`.

### Скрипт установки сервера

Мастер «Добавить сервер» в конце выдаёт команду такого вида (её же возвращает
`POST /api/v1/nodes` в поле `install_command`):

```
curl -fsSL https://panel.example.com/api/v1/install/<token>.sh | sudo bash
```

Выполните её под root на свежем сервере Ubuntu 22.04+ или Debian 12+ с архитектурой x86_64 и
публичным IPv4-адресом. Токен срабатывает один раз и действует 24 часа. Новую команду можно
получить на вкладке «Обслуживание» («Показать команду установки»), старая при этом перестаёт
работать.

Сначала скрипт выполняет проверки, которые ничего не меняют: архитектура x86_64, systemd работает,
`/healthz` панели отвечает с этого сервера, публичный IP известен, A-запись сервера указывает на
него, порты 80 и 443 свободны. На сервере с telemt он также проверяет, что свободен порт Fake-TLS
и, только в виде предупреждения, что домен Fake-TLS находится в DNS. Если не прошла проверка DNS
или портов, скрипт показывает меню:

```
  What now?  [r] re-run the checks   [c] continue anyway   [q] quit
```

На этом этапе ещё ничего не установлено. Без терминала скрипт просто останавливается. Поведение
меняют три переменные: `TGWP_SKIP_PREFLIGHT=1` продолжает несмотря на неудачные проверки,
`TGWP_DRY_RUN=1` останавливается сразу после них, `TGWP_PUBLIC_IP=a.b.c.d` задаёт публичный адрес.
Их пишут перед `bash`: `curl … | sudo TGWP_SKIP_PREFLIGHT=1 bash`.

Затем скрипт ставит движок (см. [Движки серверов](#движки-серверов)). Caddy должен получить
сертификат за 120 секунд, а на сервере с telemt telemt должен сообщить о готовности за 60 секунд.
Только после этого, последним шагом, сервер регистрируется в панели, потому что регистрация
расходует токен. Поэтому если скрипт упал до шага «Registration», устраните причину и запустите
ту же команду снова.

## Переменные окружения

Панель берёт настройки из `.env`. Все переменные перечислены в файле `.env.example`.

### Читает панель

| Переменная | По умолчанию | Что задаёт |
|---|---|---|
| `DATABASE_URL` | нет, обязательна | Строка подключения к PostgreSQL. В установке через Docker её задаёт compose-файл |
| `MASTER_KEY` | нет, обязательна | 32 случайных байта в base64. Шифрует секреты в базе |
| `MASTER_KEY_VERSION` | `1` | Версия текущего мастер-ключа |
| `MASTER_KEY_V<n>` | нет | Старые мастер-ключи, для каждой версии ниже текущей |
| `MASTER_KEY_NEW` | нет | Только для `panel keys rotate`: новый ключ |
| `SESSION_SECRET` | нет, обязательна | 32 случайных байта в base64. Подписывает сессионные cookie |
| `PANEL_HTTP_ADDR` | `:8080` | Где панель принимает HTTP и gRPC |
| `PANEL_PUBLIC_URL` | `http://localhost:8080` | Публичный адрес панели, он попадает в команды установки и нужен агентам. Без слеша в конце |
| `DATA_DIR` | `./data` (`/data` в образе) | Бинарник агента, который панель раздаёт серверам, и резервные копии |
| `NODE_DRIVER` | `gateway` | `gateway` для настоящих серверов, `mock` для демо и тестов |
| `METRICS_TOKEN` | нет | Защищает `/metrics`. Обязательна при `gateway` |
| `TPROXY_COMMIT` | `52a5feb7fac38f68da5afef9cedd9b3bfc8473ca` | Коммит `tproxy-server` для новых серверов с tproxy, от 7 до 40 шестнадцатеричных символов в нижнем регистре |
| `TELEMT_VERSION` | `3.5.14` | Релиз telemt для серверов с telemt, вида `3.5.7` |
| `TELEMT_SHA256_X86_64` | нет, заполнена в `.env.example` | sha256 файла `telemt-x86_64-linux-gnu.tar.gz` этого релиза. Обязательна при `gateway`. Меняйте вместе с `TELEMT_VERSION` |
| `FEATURE_TOTP` | `true` | `false` прячет двухфакторный вход |
| `TRUST_FORWARDED_FOR` | `true` | Брать IP человека из заголовка `X-Forwarded-For`. Нужно, когда перед панелью стоит Caddy, он переписывает этот заголовок. В локальном режиме без Caddy установщик ставит `false`, иначе ограничение попыток входа можно обойти подделкой заголовка |
| `LOG_LEVEL` | `info` | `debug`, `info`, `warn` или `error` |
| `APPLY_INTERVAL` | `45` | Секунды между применениями на серверах с изменениями. Можно переопределить в «Настройки» → «Уведомления» |
| `OFFLINE_AFTER` | `90` | Секунды без сигнала, после которых сервер считается недоступным. Можно переопределить в «Настройки» → «Уведомления» |
| `GITHUB_REPO` | `greenpandorik/tgproxy-panel` | Откуда проверка обновлений берёт релизы и звёзды |
| `GITHUB_TOKEN` | нет | Необязательный токен GitHub без прав, поднимает лимит запросов к API. В логи не пишется |
| `UPDATE_CHECK` | `true` | `false` отключает все обращения к GitHub |
| `PROBE_TOKEN` | нет | Токен внешних проверок, не короче 32 символов. Нужна `PROBE_LOCATIONS` |
| `PROBE_LOCATIONS` | нет | Имена мест внешних проверок через запятую или пробел: буквы, цифры, `_` и `-` |
| `ALERT_WEBHOOK_URL` | нет | HTTPS-адрес для оповещений, без логина, параметров запроса и фрагмента |
| `ALERT_WEBHOOK_SECRET` | нет | Секрет HMAC для вебхука, не короче 32 символов |
| `BACKUP_AGE_RECIPIENT` | нет | Публичный ключ age X25519, на него шифруется каждая копия |
| `BACKUP_UPLOAD_URL` | нет | HTTPS-адрес, принимающий `PUT /<имя>.dump.age`. Нужна `BACKUP_AGE_RECIPIENT` |
| `BACKUP_UPLOAD_TOKEN` | нет | Необязательный bearer-токен для выгрузки |
| `BACKUP_VERIFY` | `false` | `true` восстанавливает каждую новую копию во временную базу для проверки. Роли базы нужно право `CREATEDB` |

Если обязательного значения нет или значение в неверном формате, панель не запускается и
сообщает, какая переменная не так.

### Читают Compose и тесты

| Переменная | Что задаёт |
|---|---|
| `PANEL_DOMAIN`, `ACME_EMAIL` | Для Caddy: домен, на который получать сертификат (по умолчанию `localhost`), и e-mail для писем о сертификате |
| `POSTGRES_PASSWORD` | Пароль встроенного PostgreSQL. Установщик генерирует его, и из него собирается `DATABASE_URL` |
| `PANEL_VERSION`, `PANEL_IMAGE` | Для `deploy/docker-compose.release.yml`: тег образа (`1.0.0`, `latest`) или полная ссылка на образ для зеркал и тестов. Записывает `install.sh` |
| `TELEMT_SHA256_MUSL_X86_64` | sha256 файла `telemt-x86_64-linux-musl.tar.gz`, нужна только демо-образу `fakenode-telemt` |
| `TEST_DATABASE_URL` | Строка подключения к PostgreSQL для `go test` |

### Читает агент

Файл `/etc/tgwp-agent/agent.env` на каждом сервере записывает скрипт установки.

| Переменная | Что задаёт |
|---|---|
| `TGWP_PANEL_URL` | Адрес панели |
| `TGWP_TOKEN` | Токен сервера. Вместо неё можно указать файл в `TGWP_TOKEN_FILE` |
| `TGWP_ENGINE` | `telemt` или `tproxy` (по умолчанию, если не задана) |
| `TGWP_TPROXY_VERSION` | На серверах с tproxy: установленный коммит |
| `LOG_LEVEL` | Уровень логов, как у панели |

У путей и адресов есть значения по умолчанию, их меняют только на тестовых стендах:
`TGWP_STATE_DIR`, `TGWP_TELEMT_API`, `TGWP_TELEMT_API_TOKEN`, `TGWP_TELEMT_API_TOKEN_FILE`,
`TGWP_TELEMT_CONFIG`, `TGWP_TELEMT_SITE_DIR`, `TGWP_TELEMT_BIN`, `TGWP_TELEMT_METRICS`,
`TGWP_TPROXY_BIN`, `TGWP_CONFIG`, `TGWP_PROFILES`, `TGWP_MTPROXY_ENV`, `TGWP_SITE_DIR`,
`TGWP_RELAY_ADMIN`, `TGWP_MTPROXY_STATS`.

### Читают скрипты установки и пробник

| Переменная | Что задаёт |
|---|---|
| `TGWP_<NAME>` | Любой параметр `install.sh` панели, например `TGWP_DOMAIN=panel.example.com TGWP_YES=1` |
| `TGWP_SKIP_PREFLIGHT`, `TGWP_DRY_RUN`, `TGWP_PUBLIC_IP` | Скрипт установки сервера, см. [Скрипт установки сервера](#скрипт-установки-сервера) |
| `TGWP_PROBE_TOKEN` | Для `tgwp-probe`: значение `PROBE_TOKEN` панели |

### Читает сервис страниц подписки

Их записывает `install.sh --subpage` в `/opt/tgproxy-subpage/.env`.

| Переменная | Что задаёт |
|---|---|
| `SUBPAGE_PANEL_URL` | Адрес панели, например `https://panel.example.com`. Обязательна |
| `SUBPAGE_TOKEN` | Токен сервиса из «Подписка» → «Сервис». Обязательна |
| `SUBPAGE_LISTEN` | На каком адресе слушать, по умолчанию `:8080` |
| `SUBPAGE_DOMAIN`, `ACME_EMAIL` | Домен страниц и e-mail для сертификата, их читает Caddy сервиса |
| `SUBPAGE_VERSION`, `SUBPAGE_IMAGE` | Какой образ запускать. Версия должна совпадать с версией панели |

## Командная строка

### `panel`

Программа панели. В установке через Docker это `/app/panel` в контейнере `panel`: пока панель
работает, используйте `docker compose exec panel /app/panel …`, а для команд, которым нужна
остановленная панель, `docker compose run --rm panel …`. Любая команда сначала применяет
недостающие миграции базы.

| Команда | Что делает |
|---|---|
| `panel serve` | Запускает панель. Это команда по умолчанию. Вторая панель на той же базе не запустится |
| `panel migrate` | Применяет миграции базы и завершается |
| `panel admin create <username> <password> [owner\|admin\|viewer]` | Создаёт учётную запись, по умолчанию с ролью `owner`. Пароль не короче 10 символов |
| `panel admin totp-reset <username>` | Выключает двухфакторный вход у одной учётной записи и удаляет её резервные коды |
| `panel db backup` | Делает резервную копию, как кнопка в настройках |
| `panel db restore <file> --yes` | Заменяет базу резервной копией. Не работает, пока панель запущена |
| `panel db verify <file>` | Восстанавливает копию во временную базу для проверки, рабочая база не меняется |
| `panel keys rotate [--dry-run]` | Перешифровывает все секреты ключом из `MASTER_KEY_NEW`. Не работает, пока панель запущена |
| `panel subpage` | Запускает сервис страниц подписки вместо панели. База ему не нужна, настройки берутся из переменных `SUBPAGE_*`, см. [Страницы подписки на своём домене](#страницы-подписки-на-своём-домене) |

### `tgwp-agent`

Агент на каждом сервере. Unit `tgwp-agent.service` запускает его без аргументов.

| Команда | Что делает |
|---|---|
| `tgwp-agent` | Запускает агента с настройками из окружения |
| `tgwp-agent version` | Печатает версию |
| `tgwp-agent upgrade [--telemt\|--agent] [--check] [--yes]` | Обновляет сервер до того, что ждёт панель, см. [Обновление серверов](#обновление-серверов). `--env` задаёт другой файл настроек, `--agent-bin` и `--telemt-bin` другие пути к бинарникам |
| `tgwp-agent init-node --engine telemt\|tproxy …` | Записывает конфигурацию движка. Её вызывает скрипт установки |

У `init-node` есть два флага только для тестовых стендов: `--no-synlimit` (без правил nftables,
для контейнеров без `CAP_NET_ADMIN`) и `--no-tls-emulation` (для домена Fake-TLS, которого нет в
DNS). Настоящие серверы работают без них.

### `tgwp-probe`

Внешняя проверка. Соберите её командой `go build -o tgwp-probe ./cmd/probe` и запускайте в другой
сети, обычно по таймеру systemd из `deploy/probe`:

```bash
TGWP_PROBE_TOKEN=<PROBE_TOKEN> tgwp-probe --panel https://panel.example.com \
  --host proxy1.example.com --node <server UUID> --location isp-a
```

`--protocol-config /path/to/private.json` включает встроенные проверки Fake-TLS и WEB с
авторизацией: успешный результат требует ответа Telegram `resPQ` с nonce исходного запроса.
Храните тестовый секрет прокси в закрытом файле, а не в аргументах. Формат конфигурации и
настройка systemd описаны в [Authenticated probes](authenticated-probes.md).
Без настроенных секретов эти проверки остаются в состоянии `not_run`.

`--client-check /absolute/path` подключает ваш собственный адаптер, который проверяет Fake-TLS и
WEB настоящим клиентом. Он получает домен на стандартный ввод, и у него есть 45 секунд, чтобы
напечатать до 4096 байт JSON. UUID сервера виден в адресе его страницы в панели.

### `install.sh`

Установщик панели. Любой параметр можно задать и переменной окружения `TGWP_<NAME>`.

| Параметр | Что делает |
|---|---|
| (без параметров) | Установка. Если `/opt/tgproxy-panel/.env` уже есть, обновление |
| `--update` | Скачать образ для `--version` (по умолчанию последний релиз) и перезапустить. Сохраняет `.env` и данные и переводит закреплённые версии telemt на значения из релиза |
| `--uninstall` | Остановить и удалить контейнеры. Спросит, удалять ли тома с данными |
| `--purge` | Вместе с `--uninstall`: удалить тома и каталог установки без вопросов |
| `--domain <fqdn>` | Домен панели |
| `--local` | Без домена: без Caddy и TLS, панель на `http://<ip>:8080` |
| `--email <address>` | E-mail для писем о сертификате |
| `--admin-user <name>` | Имя первой учётной записи (роль `owner`), по умолчанию `admin` |
| `--admin-password <pw>` | Её пароль. Если не задан, генерируется (20 символов) и печатается один раз |
| `--version <tag>` | Какой релиз ставить, например `1.0.0` |
| `--dir <path>` | Каталог установки, по умолчанию `/opt/tgproxy-panel` |
| `--image <ref>` | Другая ссылка на образ, для зеркал и тестов |
| `--from-checkout` | Взять файлы, которые лежат рядом со скриптом, без скачивания |
| `--skip-preflight` | Пропустить проверки DNS, портов и каталога установки |
| `--sub-domain <fqdn>` | Открывать страницы подписки ещё и на этом домене, на сервере панели. Его A-запись тоже должна вести на этот сервер. `off` убирает домен |
| `--subpage` | Ставить, обновлять (`--update`) или удалять (`--uninstall`, `--purge`) сервис страниц подписки вместо панели. Каталог по умолчанию `/opt/tgproxy-subpage` |
| `--panel-url <url>`, `--token <token>` | С `--subpage`: адрес панели и токен сервиса из «Подписка» → «Сервис». С `--subpage` параметр `--domain` задаёт домен страниц |
| `--yes` | Ничего не спрашивать. Если не хватает обязательного значения, это ошибка |
| `--help` | Показать список параметров |

## API для скриптов

Веб-интерфейс и скрипты обращаются к `/api/v1/…` на вашей установленной панели. Создайте
персональный токен в «Настройки» → «API-токены» и передавайте `Authorization: Bearer <токен>`
по HTTPS. Секрет показывается один раз; срок по умолчанию — 30 дней, допустимо 1–365 дней.
Доступ ограничен и разрешениями токена, и текущей ролью учётной записи. Примеры curl/Python
есть в [руководстве API](api.ru.md), разрешённые адреса — в [каталоге методов](https://tgproxypanel.com/api/#routes)
и [спецификации OpenAPI](https://tgproxypanel.com/api/openapi.json).

Проверенный персональный Bearer-токен не требует CSRF-заголовка. Браузерный сеанс использует
cookie от `POST /api/v1/auth/login`; изменения по-прежнему требуют `X-CSRF-Token`, равный `tgwp_csrf`.
Управление токенами, паролем/2FA, учётными записями, резервными копиями и реквизитами сервиса
подписки требует браузерного сеанса. Авторизация агентов, метрик и сервиса подписки отдельная.
В таблице ниже есть эти другие способы авторизации, а также адреса автоматизации:

| Адрес | Доступ | Что возвращает |
|---|---|---|
| `GET /healthz` | Публичный | `ok`, пока панель работает |
| `GET /metrics` | `METRICS_TOKEN` | Метрики Prometheus, см. [Мониторинг](#мониторинг) |
| `GET /s/{token}`, `GET /s/{token}.json` | Публичный | Страница подписки, см. [Страница подписки](#страница-подписки). Вместо токена подходит короткий адрес |
| `GET /api/v1/subscription-service` | Владелец, администратор | Настройки и состояние сервиса страниц подписки |
| `PUT /api/v1/subscription-service` | Владелец | Сохранить `{public_url, hide_on_panel}` |
| `POST /api/v1/subscription-service/token` | Владелец | Новый токен сервиса, ответ `{token, command}` |
| `DELETE /api/v1/subscription-service/token` | Владелец | Отозвать токен сервиса |
| `GET /api/v1/subpage/pages/{token}`, `POST /api/v1/subpage/heartbeat` | Токен сервиса | Данные одной страницы и сигнал «на связи», для сервиса страниц подписки |
| `GET /api/v1/keys` | Любая роль | Список пользователей. Параметры `q`, `type`, `node`, `state`, `page`, `per_page` |
| `GET /api/v1/keys/summary` | Любая роль | Числа для кнопок состояний над списком: `{total, active, expiring, expired, disabled, revoked}` |
| `POST /api/v1/keys`, `PATCH /api/v1/keys/{id}` | Владелец, администратор | Создать или изменить пользователя |
| `POST /api/v1/keys/{id}/disable`, `POST /api/v1/keys/{id}/enable` | Владелец, администратор | Выключить или включить доступ |
| `POST /api/v1/keys/bulk` | Владелец, администратор | Одно действие над несколькими пользователями: `extend`, `disable`, `enable`, `revoke` или `delete` |
| `POST /api/v1/keys/import` | Владелец, администратор | Пользователи из другого прокси со своими секретами, все или никто |
| `POST /api/v1/keys/{id}/subscription` | Владелец, администратор | Новая ссылка подписки вместо прежней, ответ `{url, qr_data_uri}` |
| `GET /api/v1/keys/{id}/subscription/qr` | Владелец, администратор | PNG с QR-кодом текущей ссылки подписки |
| `GET /api/v1/keys/{id}/links` | Владелец, администратор | Прямые ссылки пользователя, сгруппированные по серверам |
| `GET /api/v1/monitoring/overview?from&to&step` | Любая роль | Ряды данных для графиков мониторинга |
| `GET /api/v1/dashboard/trends` | Любая роль | Последние сутки для «Обзора»: `{people: [{t, people_online}], traffic_24h, traffic_prev_24h}` |
| `PUT /api/v1/nodes/order` | Владелец, администратор | Задать порядок серверов: `{ids: [...]}` |
| `GET /api/v1/alerts` | Любая роль | Открытые проблемы, которые никто не отметил прочитанными |
| `POST /api/v1/alerts/resolve` | Владелец, администратор | Отметить проблемы прочитанными: `{ids: [...]}`, ответ `{resolved}` |
| `GET /api/v1/audit` | Любая роль | Журнал действий |
| `GET /api/v1/nodes/{id}/metrics` | Любая роль | Собственные метрики прокси на сервере в формате Prometheus |
| `GET /api/v1/nodes/{id}/blocklist` | Любая роль | Чёрный список сервера, состояние на сервере и счётчики отброшенных пакетов |
| `PUT /api/v1/nodes/{id}/blocklist` | Владелец, администратор | Заменить чёрный список: `{revision, entries: [{prefix, note}]}`, до 2000 записей; если список успели изменить после `revision`, ответ 409 |
| `GET /api/v1/status/update` | Любая роль | Результат проверки обновлений |
| `GET /api/v1/node/upgrade` | Токен сервера | Что должно работать на сервере, для `tgwp-agent upgrade` |

`GET /api/v1/keys/{id}/links` отвечает
`{items: [{node_id, node_name, hostname, engine, links: [{kind, domain, tme, tg}]}], client_support}`.
`kind` равен `web` или `tls`, а `domain` называет домен маскировки для ссылки `tls`.

Пользователь в ответах API описан объектом ключа. Кроме прежних полей (`id`, `label`, `type`,
`owner_label`, `status`, `expires_at`, `nodes` и других) в нём есть:

| Поле | Что значит |
|---|---|
| `state` | `active`, `pending`, `disabled`, `expired` или `revoked`, как в списке |
| `disabled_at` | Когда доступ выключили, или `null` |
| `last_seen_at` | Когда человек подключался последний раз, или `null` |
| `sub_slug` | Короткий адрес общего доступа, или `null` |
| `subscription_url`, `subscription_short_url` | Ссылка подписки и короткая ссылка, или `null`. Есть только в ответах владельцу и администратору |
| `subscription_legacy` | `true`, если ссылка выпущена прошлой версией панели и показать её нельзя. Тоже только для владельца и администратора |
| `live` | `{online, connections, devices, devices_15m, ips}` по всем серверам с telemt: `online`, когда есть хотя бы одно соединение, `devices` — разные IP-адреса прямо сейчас, `devices_15m` — за последние 15 минут; `ips` повторяет `devices` |

Фильтр `state` в `GET /api/v1/keys` принимает `active`, `pending`, `expiring` (срок кончается в
ближайшие 7 дней), `expired`, `disabled` и `revoked`. `POST /api/v1/keys` и
`PATCH /api/v1/keys/{id}` принимают `sub_slug`, но только у общего доступа; занятый адрес даёт
422 с `sub_slug: "taken"` в `error.fields`. `POST /api/v1/keys/bulk` принимает
`{action, ids, expires_at}`, от 1 до 500 идентификаторов, `expires_at` нужен только для `extend`.
`POST /api/v1/keys/import` принимает поля `POST /api/v1/keys` и
`items: [{label, owner_label, secret}]`, от 1 до 500 штук, секрет из 32 шестнадцатеричных
символов. Плохая строка даёт 422 с `items.<номер>` в `error.fields`, в том числе секрет, который
уже есть у другого пользователя; тогда не создаётся никто.
`GET /api/v1/keys/{id}/subscription/qr` принимает `size` от 128 до 1024 (по умолчанию 256), а
с `short=1` рисует короткий адрес.

`GET /api/v1/monitoring/overview` возвращает
`{nodes: [{node_id, node_name, hostname, status, cert_expires_at}], series: {<node_id>: [{t, sessions_live, streams_live, people_online, bytes_up_rate, bytes_down_rate}]}, fleet: {people_online, people_online_15m, connections}}`.
`from` и `to` задают время в формате RFC 3339, по умолчанию это последние 24 часа. Промежуток не больше
31 дня, потому что снимки хранятся 30 дней; на более широкий панель отвечает 400. Скорости
указаны в байтах в секунду и считаются по соседним снимкам, а сброс счётчика (перезапуск relay)
даёт 0. При `step` больше 60 секунд база группирует данные в интервалы такой длины. Для каждого
сервера возвращается не больше 600 точек. То же ограничение промежутка действует для
`GET /api/v1/monitoring/nodes/{id}/series`, у её точек тоже есть `people_online`. У снимков,
сделанных до того, как панель начала считать людей, `people_online` равно `null`, а числа `fleet`
равны `null`, если последнему подсчёту больше трёх минут. В `GET /api/v1/dashboard/summary` те же
`people_online` и `people_online_15m` стоят рядом с `sessions_live`, а у каждого сервера в
`GET /api/v1/nodes` и `GET /api/v1/nodes/{id}` есть `people_online` и `connections` из его
последнего снимка за три минуты или `null`. У серверов, помеченных как не в сети, их нет, и
`sessions_live`, `streams_live`, `bytes_up` и `bytes_down` в сводке складываются только по
остальным. `cert_expires_at` — когда истекает TLS-сертификат на порту 443, по последней
диагностике, которая его прочитала, или `null`. У сервера в `GET /api/v1/nodes` есть ещё
`dirty_since` — когда появились его неприменённые изменения, или `null`, если ничего не ждёт или
время неизвестно.

`PUT /api/v1/nodes/order` ставит перечисленные серверы первыми в заданном порядке, а остальные
оставляет за ними в прежнем порядке; id, которым не соответствует ни один сервер, пропускаются.
Пустой список, больше 1000 id или повтор одного id дают 400. Ответ — `{ids}` со всеми серверами в
новом порядке.

`GET /api/v1/dashboard/trends` даёт людей онлайн за последние 24 часа с шагом 20 минут и трафик
всех серверов за последние 24 часа как сумму шагов их счётчиков, поэтому перезапуск его не
теряет. `traffic_prev_24h` — такая же сумма за предыдущие 24 часа, она равна `null`, если
сохранённая история не покрывает эти сутки целиком; `traffic_24h` равен `null`, пока ни у одного
сервера нет двух показаний.

`POST /api/v1/alerts/resolve` принимает от 1 до 500 id и отмечает те, что ещё открыты и не
прочитаны; в ответе — сколько отмечено. Проблема, появившаяся после загрузки списка, в него не
попала и остаётся. Прочитанная проблема пропадает из `GET /api/v1/alerts` и из сводки, но остаётся
открытой, пока не решится. `POST /api/v1/alerts/{id}/resolve` делает то же для одного id.
`GET /api/v1/fleet/updates` отдаёт ещё `version` — сборку telemt, которую ставит обновление.

`GET /api/v1/audit` принимает параметры:

| Параметр | Что значит |
|---|---|
| `action` | Начало названия действия: `action=key.` найдёт `key.create`, `key.revoke` и так далее |
| `user` | Точное имя пользователя |
| `from`, `to` | Время в формате RFC 3339, обе границы включительно |
| `page`, `per_page` | Постраничный вывод. `per_page` не больше 200, `page` не больше 100000 |

## Разработка и тесты

Нужны Go 1.26+, Node.js 22+ и PostgreSQL 16. Создайте базы `tgwp` и `tgwp_test` и скопируйте
`.env.example` в `.env`. В [CONTRIBUTING.md](../CONTRIBUTING.md) (на английском) перечислены
проверки перед отправкой изменений, соглашения и порядок выпуска релиза.

| Команда | Что делает |

| `make run` | `go run ./cmd/panel serve` с вашим локальным `.env` |

| `make test-node-preflight` | Проверяет начальные проверки скрипта установки сервера в `ubuntu:24.04` |
| `make test-agent-upgrade` | Проверяет `tgwp-agent upgrade` против заглушки панели |

Тесты Go запускаются по одному пакету (`-p 1`), потому что все пакеты делят одну тестовую базу.

### Демо-серверы и сквозной тест

Для обоих движков есть демо-сервер в контейнере, поэтому весь путь от панели через агента до
прокси можно проверить без VPS:

```bash
make e2e          # движок tproxy: deploy/Dockerfile.fakenode (настоящий tproxy-server и заглушка MTProxy)
make e2e-telemt   # движок telemt: deploy/Dockerfile.fakenode-telemt (настоящий бинарник из релиза telemt)
```

Каждая цель поднимает PostgreSQL и панель на `:8080`, создаёт администратора и сервер, запускает
демо-сервер с новым токеном установки, создаёт пользователя, применяет его и проверяет, что
прокси его получил. Прогон tproxy ещё и назначает сайт `corporate`. В конце печатается
`SMOKE OK`, и стенд удаляется вместе с томами.

Чтобы стенд с telemt остался работать и его можно было посмотреть, выполните шаги сами:
`deploy/e2e-smoke-telemt.sh` печатает токен установки,
`docker compose --profile dev-telemt up -d --build fakenode-telemt` запускает сервер, а
`deploy/e2e-smoke-telemt.sh --continue` выполняет проверки. `docker compose logs fakenode-telemt`
показывает запуск сервера, а `docker compose exec fakenode-telemt journalctl -u telemt` показывает
лог telemt.

Образ с telemt скачивает `telemt-x86_64-linux-musl.tar.gz` и сверяет его с
`TELEMT_SHA256_MUSL_X86_64`. telemt собирается только для x86_64, поэтому на машине с arm64
контейнер работает в эмуляции и медленнее. Демо-сервер отличается от настоящего в трёх местах, и
все они вызваны контейнером: в нём нет Caddy, а `init-node` запускается с `--no-synlimit` и
`--no-tls-emulation`.

`make e2e-telemt` нужен выход в интернет к датацентрам Telegram. Пока telemt не достучится хотя бы
до одного, его `/v1/health/ready` отвечает `no_healthy_upstreams`, и сервер не выходит из
`pending`. Причину покажет `docker compose exec fakenode-telemt journalctl -u telemt`.
