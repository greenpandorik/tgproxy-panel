# Надёжность и новая навигация

Главная страница показывает состояние парка и проблемы. «Парк серверов» содержит
список нод и последовательное обновление. Разделы ноды — вкладки над содержимым,
в трёх группах: наблюдение (состояние, WEB, статистика, диагностика, логи), настройка
(прокси, профили, сайт), обслуживание (версии, обновления, установка, перезапуск, удаление).
Настройки панели отделены от личных предпочтений и оформления. Раздел сохраняется
в URL; работают обновление страницы, прямые ссылки и кнопка браузера «Назад».

## Обновление существующей установки

Обновить панель и агенты. Миграции добавляют `probe_reports` и `fleet_rollouts`.
Старые агенты продолжают отдавать прежние поля; новые показания будут недоступны
до обновления агента. Новые восстановление и маршрутизация изначально выключены.
Плановая диагностика выполняется автоматически: максимум одна нода за цикл,
повторно не чаще одного раза в 15 минут. Она создаёт/закрывает инциденты по отдельным
проверкам, в том числе сертификату и каждому опубликованному IP (до восьми адресов).

### Обновление парка

Открыть «Парк серверов → Обновление парка», отметить онлайн-ноды telemt в нужном
порядке. Первая нода служит контрольной. Используется закреплённая версия и SHA256
панели, обязательное завершение WEB-сессий, проверка агента и проверка со стороны
панели. Через минуту после успешного результата повторно проверяется здоровье,
затем очередь переходит дальше. Ошибка останавливает оставшиеся обновления.
Кнопка остановки не прерывает уже начатую операцию.

Очередь сохраняется в PostgreSQL. При неоднозначном обрыве передачи команды
панель останавливает очередь и просит проверить ноду, не отправляя команду повторно.
Агент перед изменением бинарника сохраняет fsync-журнал, проверенные по SHA256
бинарник и конфигурацию. При запуске после прерванного обновления восстанавливает
их и исходный режим приёма WEB-сессий. Если восстановление не удалось, новые Apply,
маршрутизация и обновления блокируются. Проверить журнал агента, устранить причину
(например, нехватку места), перезапустить агент. Не удалять журнал вслепую.
Артефакты `telemt-known-good*` сохраняются до следующего обновления.

### Локальное восстановление и маршруты

«Нода → Прокси → Надёжность и маршрут до Telegram». Режим наблюдения ничего
не перезапускает. Opt-in перезапуск требует последовательных неудач (по умолчанию
3 проверки по 30 секунд), выдерживает паузу 300 секунд и бюджет 2 действия в час.
Режим обслуживания и намеренно закрытый WEB-приём подавляют восстановление.
Намеренно остановленный systemd-сервис не запускается автоматически.

Маршрут применяется только к исходящим соединениям telemt, без изменения маршрутов
хоста. SOCKS5 должен слушать loopback этой ноды: локальный WARP либо другой туннель
нужно установить отдельно. Основной и резервный маршруты проверяются на TCP-доступ
к двум Telegram DC; это не доказательство работоспособности MTProto-клиента.
Middle Proxy / спонсорский тег несовместимы с SOCKS/WARP. После failover возврат
на основной выполняется явной кнопкой с повторной проверкой. Для возврата к ручной
маршрутизации сначала выбрать прямой маршрут. Маршруты с отдельными scopes сохраняются.

### Внешние пробники

Панель: задать `PROBE_TOKEN` (минимум 32 случайных символа) и
`PROBE_LOCATIONS=isp-a,isp-b`. В каждой независимой сети собрать
`go build -o tgwp-probe ./cmd/probe` и установить бинарник в `/usr/local/bin`.
Пример systemd service/timer и переменных находится в `deploy/probe`. Файл переменных
разместить в `/etc/tgwp-probe/<имя>.env` с правами 0600, units — в `/etc/systemd/system`,
затем `systemctl daemon-reload` и `systemctl enable --now tgwp-probe@<имя>.timer`.
Один экземпляр проверяет одну ноду; UUID виден в URL карточки ноды.

Встроены реальный TLS-handshake с проверкой сертификата и HTTP GET сайта.
Отчёт старше трёх минут считается устаревшим; отсутствие отчёта создаёт инцидент.
Поддельный старый отчёт не заменяет более свежий. Не включать ожидаемые сети,
в которых пробник ещё не развёрнут, иначе появятся ожидаемые инциденты отсутствия данных.

Проверка настоящих клиентов подключается через `--client-check /absolute/checker`.
Это адаптер для установленного в вашей сети клиента, а не встроенный Telegram-клиент.
Процесс получает hostname с переводом строки на stdin, имеет 45 секунд и должен
вернуть до 4096 байт JSON:

```json
{"faketls":{"status":"ok","latency_ms":120},"web":{"status":"not_run","latency_ms":0}}
```

Допустимы `ok`, `failed`, `not_run`. `ok` должен означать успешный обмен через
соответствующий прокси, а не только открытый порт. Секреты хранить в отдельном
0600-файле, доступном сервису; не передавать их в аргументах и не печатать. Для
checker, читающего личную session-базу, настроить отдельного непривилегированного
пользователя и доступ к каталогу вместо DynamicUser. Без checker обе клиентские
проверки честно остаются «Не проверено». Реальные FakeTLS/WEB сценарии требуют
ваших рабочих ключей и независимых сетей и не были выполнены локально.

### Независимые уведомления

`ALERT_WEBHOOK_URL` — HTTPS endpoint, `ALERT_WEBHOOK_SECRET` — минимум 32 символа.
Webhook работает независимо от включения Telegram-бота. Тело содержит `event_id`,
`node_id`, `kind`, `message`, `at`. Проверять HMAC-SHA256 заголовка
`X-TGWP-Signature` от `X-TGWP-Timestamp + "." + сырое тело`, отклонять старые
метки времени и дедуплицировать `event_id`. До трёх попыток, без HTTP-редиректов.
Инциденты сохраняются в БД; доставка webhook имеет ограниченные повторы, отдельной
долговечной очереди доставки нет. Для отказа самого хоста панели нужен внешний
мониторинг её `/healthz` — панель не сможет отправить сообщение, будучи выключенной.

### Защита резервных копий

`BACKUP_AGE_RECIPIENT` — публичный X25519 recipient age. Закрытый ключ хранить вне
сервера панели. `BACKUP_UPLOAD_URL` — HTTPS base URL, принимающий PUT
`/<имя>.dump.age`; `BACKUP_UPLOAD_TOKEN` — необязательный bearer. В сеть отправляется
только зашифрованный файл. Локальная копия сохраняется для существующего сценария
скачивания и восстановления. Статус шифрования, загрузки и проверки виден в
«Настройки панели → Резервные копии». Неудача защиты не скрывает локальную копию.

`BACKUP_VERIFY=true` после создания выполняет восстановление в новую временную
БД `tgwp_restore_<uuid>`, проверяет таблицу nodes и расшифровку сохранённых секретов
всеми настроенными версиями MASTER_KEY, затем удаляет тестовую БД. Роли нужен CREATEDB.
Это создаёт дополнительную нагрузку и требует места примерно под ещё одну БД.
Ручная проверка: `panel db verify <имя.dump>`; она не меняет рабочую БД.

Для восстановления вне хоста сначала расшифровать `.age` с сохранённым закрытым
ключом (`age --decrypt -i <identity> -o <имя.dump> <имя.dump.age>`), затем использовать
существующий `panel db restore <имя.dump> --yes`. Сохранить MASTER_KEY и все старые
MASTER_KEY_V<n> отдельно: зашифрованный дамп не заменяет ключи приложения.
